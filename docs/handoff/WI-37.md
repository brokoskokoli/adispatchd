## Entscheidungen und Abweichungen

1. **Layout:** Der Standard von `hub init` (Workspace-Daten unter dem Hub-config-dir) ist für den Dienstbetrieb ungeeignet, weil
   `service install` das config-dir `root` übereignet und schreibgeschützt macht. Statt den Standard zu ändern (WI-35-Tests, Rückwärtsverhalten) gibt es
   `--workspaces-data-dir`; `service install --hub` lehnt das Trial-Layout mit genau diesem Hinweis ab. Empfohlen: config unter `/etc/adispatchd-hub`,
   Hub-data-dir `/var/lib/adispatchd-hub/hub`, Workspace-data-dirs `/var/lib/adispatchd-hub/workspaces/<id>`. Das Hub-data-dir darf **nicht**
   über den Workspace-data-dirs liegen (verschachtelt verboten), daher das Unterverzeichnis `hub/`.
2. **KillMode und Timeouts** (Begründung aus WI-35/36 übernommen): `KillMode=mixed` (SIGTERM nur an den Hub; der Hub gibt jedem Workspace genau ein SIGTERM weiter,
   die Workspaces drainen parallel, der Hub endet, wenn alle Kinder weg sind; Default `control-group` würde alle Worker sofort abbrechen).
   `TimeoutStopSec` = Drain + Cancel + max(`cancel_grace` über **alle** Workspaces) + 60 s; passt zur SIGKILL-Frist des Supervisors
   (Drain + Cancel + 30 s je Kind). Die Hub-Flags `--drain-timeout/--cancel-timeout` werden an `hub start` übergeben und von dort an die Kinder weitergereicht.
   Stirbt der Hub unter `mixed`, beendet systemd die ganze cgroup (Recovery der Workspaces → `crashed`); das „Workspaces überleben“-Verhalten
   (WI-35 Entscheidung 4) gilt nur ohne systemd/`KillMode=process` und ist so dokumentiert.
3. **`hub drain-all|stop-all --wait`** (in den WI-35/36-Handoffs als Folgeschritt genannt) ist nötig für den dokumentierten Update-Ablauf
   (`hub drain-all --wait`, dann `systemctl stop`), weil `drain-all` sonst sofort zurückkehrt. Der Hub läuft nach `drain-all` weiter (Workspaces `stopped`).
4. **Migration:** kein eigener Befehl, sondern ein dokumentierter Ablauf (`hub init --empty`, Eintrag in `hub.yaml`, alte Unit draimen/abschalten, Env-Datei
   zusammenführen, `hub validate`, `service install --hub`). `server.port` der Instanz wird vom Hub überschrieben (`--port`); die Instanzsperre verhindert
   zwei Prozesse auf demselben data-dir (Test: `src/cli/hub.test.ts` „migrating a single instance“, E2E im Paket-Test).
5. **Env-Datei:** eine für den ganzen Hub, alle Workspaces erben sie; getrennte Variablennamen je Workspace sind Konvention (in der Vorlage und in operations.md erklärt), kein technischer Zwang.
6. **Nicht umgesetzt / bewusst offen:** Reload von `hub.yaml`, Adopt verwaister Instanzen, ein Hub-eigener `service`-Befehl für das Zusammenführen der Env-Dateien
   (manuell dokumentiert), `examples/config` unverändert (die Instanz-Konfiguration hat sich nicht geändert; das Hub-Beispiel liegt in `examples/hub/`).
   Unix-Socket statt Loopback-Port zur Instanz, Zugriffsrechte je Workspace und Screenshots der Übersicht bleiben Folgeschritte aus dem Handoff WI-36.
