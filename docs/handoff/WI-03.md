### Schema (Migration v1)
Tabellen aus §12 plus Ergänzungen:
- `runs`: alle §12-Spalten + `lock_key`, `scheduled_for`, `identity`, `command` (JSON), `final_status`, `final_reason`
  (zusammen mit `business_result` = persistiertes `FinalizationTarget`), `status_message`, `result_json`, `error_json`,
  `lifecycle_status`, `block_generation`, `counted_technical_failure`, `created_at`, `finalizing_at`, `updated_at`.
  CHECK-Constraints für Status/Ergebnis/Trigger. Partieller Unique-Index `(workflow_id, lock_key) WHERE status IN (aktiv)`
  als zweite Absicherung neben `locks`.
- `locks (workflow_id, lock_key) PK`, `run_id UNIQUE` → `runs`.
- `run_events`: `id INTEGER PRIMARY KEY AUTOINCREMENT` (global, nie wiederverwendet), `UNIQUE(run_id, sequence)`,
  zusätzlich `origin` (`worker|orchestrator`).
- `run_actions` (`UNIQUE(run_id, hook, ordinal)`, `action_type`, `action_name`, `attempts`, `last_error_json`),
  `action_attempts` (`UNIQUE(run_action_id, attempt)`, `outcome`, `external_key`).
- `blocks` (+ `run_id`, `failure_count`, `cleared_by`; partieller Unique-Index: max. ein aktiver Block je
  `(workflow_id, COALESCE(source_item_key,''))`), `failure_counters`, `notifications` (+ `last_error`,
  `next_attempt_at`, `delivered_at`), `cron_firings (workflow_id, scheduled_for) PK`, `schema_migrations`.
- Log-Trunkierung/Schreibfehler: **keine eigene Tabelle**, sondern `run_events` mit `origin='orchestrator'`,
  Typ `diagnostic.<log_truncated|log_write_error|event_parse_warning|kill_failed>` (`appendDiagnostic`).
- FKs: Events/Actions/Attempts `ON DELETE CASCADE`; `blocks.run_id`/`cron_firings.run_id` `SET NULL`; `locks` `RESTRICT`.

### Migrationen & Backup
- Jede Migration in eigener Transaktion inkl. `schema_migrations`-Zeile; Fehler → Rollback + `MigrationError`.
- Backup **nur**, wenn die DB-Datei vor dem Öffnen existierte (Größe > 0) **und** Migrationen ausstehen:
  `VACUUM INTO data-dir/backups/orchestrator-<alteVersion>-<YYYYMMDDTHHMMSSmmmZ>.sqlite` (konsistent auch im WAL-Modus).
- DB mit höherer Version als der Build kennt → `MigrationError` (kein Start, kein stilles Downgrade).

## Verträge für Konsumenten

### RunRepository (WI-08/WI-09/WI-10)
- `reserve({workflowId, triggerType, sourceId?, sourceItemKey?, sourceUrl?, scheduledFor?, configSnapshot, parameters?,
  identity?, command?, workspacePath?, id?, failIfBlocked?})` – atomar: Lock prüfen+anlegen, Run `reserved`, Event.
  `LockConflictError` bei aktivem Lock (`holderRunId`). `failIfBlocked: true` (Scheduler) prüft aktiven Block in derselben
  Transaktion → `BlockedError`; manuelle Starts lassen es weg (umgehen Blocks, nicht den Lock).
- `transition(runId, to, {expectedFrom?, update?})` – nur Nicht-Endzustände (`starting`, `running`, `cancelling`,
  `recovery_pending`); geprüft mit core `canTransition`. `→ running` setzt `started_at`, falls leer.
  `finalizing`/Endstatus hier → `InvalidTransitionError`.
- `beginFinalization(runId, target: FinalizationTarget, {update?, blockPolicy?: {maxTechnicalFailures, reason?}})`
  → `{run, technicalFailure, consecutiveTechnicalFailures, blockCreated}`. **Eine Transaktion**: Zieltarget validieren
  (`completed` ⇔ `businessResult` success|failure, sonst `null`), `X → finalizing`, `final_status/business_result/final_reason`,
  Fehlerzähler anwenden, ggf. Block anlegen (wenn Limit erreicht und noch kein aktiver Block). WI-08 sendet bei
  `blockCreated` die Notification `retry_block_created` und führt danach den Hook aus.
- `finish(runId, {update?})` – `finalizing → final_status` (genau das persistierte Ziel), `finished_at`, Lock-Freigabe, Event.
- `update(runId, RunUpdate)` – pid, `processStartIdentity`, Workspace, `lifecycleStatus`, `exitCode`, `result`, `error`,
  `configSnapshot`, `identity`, `command`, `statusMessage`, `startedAt`.
- Abfragen: `get/require`, `listActive(workflowId?)`, `countActive(workflowId?)` (alle Trigger inkl. manuell),
  `list({workflowId, statuses, triggerType, sourceItemKey, businessResult, createdBefore, limit≤500, offset})` →
  `{runs, total}` (neueste zuerst), `lastRunForItem(key, {workflowId?, finishedOnly?})`, `lastRunsForItems(keys, …)` →
  `Map` (Views `run.last_*`), `activeLock`, `activeRunForItem(workflowId, itemKey)`, `listLocks()`.
- Jede Statusänderung erzeugt ein `run.status`-Event (`{from, to, target?, blockId?}`) in derselben Transaktion –
  damit sind Transitionen über SSE `Last-Event-ID` nachlieferbar.
- `Repositories.transaction(fn)` erlaubt WI-08, mehrere Repository-Aufrufe atomar zu bündeln (verschachtelt via Savepoints).

### Lock-Key-Semantik
| Run | `lock_key` | Wirkung |
|---|---|---|
| mit Item (`source` oder `manual` mit Item) | `item:<sourceItemKey>` | max. ein aktiver Run je Workflow+Item, auch manuell |
| `schedule` ohne Item | `cron:<scheduled_for ISO-UTC>` | max. ein Run je Cron-Slot (zusätzlich `cron_firings`-PK); Überlappung verschiedener Slots regelt `max_concurrent` |
| `manual` ohne Item | `manual:<runId>` | eindeutig, nie Konflikt |

Präfixe halten Namensräume getrennt (eine Source könnte `cron` heißen). Lock gilt pro Workflow → verschiedene Workflows
dürfen dasselbe Item parallel bearbeiten. Der Lock bleibt in allen aktiven Zuständen inkl. `finalizing` und
`recovery_pending` bestehen. **Block-/Zähler-Scope** ist davon getrennt: `source_item_key`, bzw. Workflow-Scope
(`itemKey = null`) für sourcefreie Runs (§11).

### Fehlerzähler-Design (Begründung)
Explizite Tabelle `failure_counters (workflow_id, scope_key, consecutive, generation)` statt Ableitung aus `runs`:
- Aktualisierung ausschließlich in der Transaktion `X → finalizing`; dieser Übergang ist laut Zustandsmaschine pro Run
  genau einmal möglich → exakt-einmal-Zählung auch bei Crash/Recovery, ohne Zeitstempel-Vergleiche.
- `crashed|start_error|timed_out` → +1; `completed`+`success` → 0; `completed`+`failure` und `cancelled` → unverändert.
- `clear(blockId)` setzt `consecutive = 0`, `generation + 1` (neue Zählperiode); Runs/Blocks bleiben erhalten.
- Auditierbar: jeder Run speichert `block_generation` und `counted_technical_failure`; `blocks.affectedRunIds(id)`
  liefert die gezählten Runs der Block-Periode (GUI „betroffene Runs“).
- Manuelle Runs zählen mit (gleiche Workflow/Item-Kombination); ein Erfolg setzt den Zähler zurück, hebt einen aktiven
  Block aber **nicht** auf (nur manuelles Entblocken). Weitere Fehler bei aktivem Block erzeugen keinen zweiten Block.
- `blockPolicy` übergibt WI-08 aus dem Run-Snapshot (`max_technical_failures`); ohne Policy wird nur gezählt.

### RetentionRepository (WI-10)
`runCandidates('successful'|'failed', olderThan, limit)` → `{runId, workflowId, finishedAt, workspacePath}`;
`successful` = `completed`+`success`, `failed` = alle übrigen Endzustände. Schutz (auch in `deleteRun` erneut in derselben
Transaktion geprüft): nicht-terminale Runs / Lock-Halter, `lifecycle_status ∈ {pending, running, failed}`, Actions
`pending|running`, aktiver Block für Workflow+Scope. `isRunProtected`, `deleteRun` (kaskadiert Events/Actions/Attempts;
Dateien/Workspaces löscht WI-10 selbst, Workspace-Pfad vorher gegen `base_dir` prüfen), `deleteClearedBlocks`,
`deleteNotifications` (nur nicht-`pending`), `deleteCronFirings` (behält je Workflow den jüngsten Slot).

### Instanz-Lock (Ansatz)
`acquireInstanceLock(dataDir)` → `{path, held, release()}`; wirft sofort `InstanceLockedError` (`instance_locked`).
- `data-dir/orchestrator.lock` ist eine Mini-SQLite-DB, geöffnet mit `locking_mode=EXCLUSIVE`; nach der ersten
  Schreibtransaktion hält SQLite die EXCLUSIVE-Dateisperre (POSIX `fcntl` bzw. `LockFileEx`) bis zum Schließen.
- Das Betriebssystem gibt die Sperre bei Prozessende **immer** frei (auch SIGKILL/Absturz) → ein „Stale Lock“ ist
  automatisch frei; es gibt keine PID-/Startzeit-Heuristik, die je zwei Instanzen zulassen könnte. Gegenüber
  `O_EXCL`+Stale-Erkennung entfällt das Übernahme-Rennen (zwei Prozesse erkennen gleichzeitig „stale“).
- Innerhalb eines Prozesses verfolgt SQLite Sperren pro Inode → zweiter Versuch im selben Prozess wird ebenfalls
  abgelehnt; ein fehlgeschlagener Versuch schwächt die gehaltene Sperre nicht (Test mit Kindprozess).
- `orchestrator.lock.json` (pid, hostname, acquiredAt) dient nur der Fehlermeldung, entscheidet nie über Besitz.
- Einschränkung: data-dir muss auf lokalem Dateisystem liegen (`fcntl` auf NFS unzuverlässig) – in WI-12-Doku aufnehmen.
- Reihenfolge in WI-10 `createApp`: `acquireInstanceLock` → `openPersistence` → …; `release()` beim Stop nach `close()`.

## Bewusste Entscheidungen / Abweichungen
- `locks` hat `lock_key` (+ `source_item_key` zur Anzeige) statt nur `source_item_key` – nötig für sourcefreie Runs.
- Events tragen `origin`; Worker können so keine Orchestrator-/Diagnose-Events vortäuschen.
- `runs.lifecycle_status` ist nullable (noch kein Hook gelaufen); gepflegt von WI-07/WI-08 via `runs.update`.
- `createJournal` ist pro `(run, hook)` idempotent; ein zweiter Durchlauf desselben Hooks im selben Run ist nicht vorgesehen.
- Runs werden standardmäßig mit `createRunId({clock})` erzeugt; eigene ID per `id` möglich.
- Retention: Runs mit `failed`-Action, deren Kette per `continue_on_error` beendet wurde, sind löschbar, sofern
  `lifecycle_status` nicht `failed` ist – maßgeblich ist der Kettenstatus, den WI-07 setzt.
