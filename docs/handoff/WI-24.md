## Entscheidungen / Abweichungen

- **`name` auch an `shell_filter`** (anderes Schema als Conditions, aber gleich nützlich; Work-Item „falls gleiches Schema“).
- **API-Änderung:** `conditions` der Workflow-Ansicht war `{workflow: n, item: n}` und ist jetzt das Objekt mit Listen
  (im CHANGELOG unter „Geändert“). Kein Kompatibilitätsfeld.
- **SSE `workflow.conditions`** trägt nur `{workflowId}` (keine stderr-Zeilen im Stream); die UI lädt per REST nach.
- **Status `skipped`** (grau) für Workflow-Conditions, die wegen einer früheren nicht ausgeführt wurden – der vorherige
  Wert wird dabei überschrieben (zeigt den Stand der letzten Auswertung).
- **Info-Skripte:** Exit 1 ist (anders als bei Conditions) ein Fehler; Schwellwerte inklusiv (≥ / ≤), `critical` vor
  `warn`, above/below kombinierbar; `unit` nur bei `number` (percent zeigt `%`); Zahl darf mit der konfigurierten
  `unit` enden. Keine `secrets` (V1), keine Templates in `args`. Kontext über die vorhandene Variable
  `ADISPATCH_CHECK_CONTEXT_FILE` (`kind: dashboard_info`) plus drei neue `ADISPATCH_*`-Variablen.
- **Skript-Existenz** wird nur für `dashboard.yaml` geprüft (Conditions prüfen das bis heute nicht; Work-Item sagt
  „wie bei Conditions“ – dort gibt es die Prüfung nicht). Bare Namen (`df`) werden nicht geprüft.
- **Ohne `dashboard.yaml`** wird der Bereich ausgeblendet (kein Hinweis), API meldet `configured: false`.
- Anzeigename ohne `name`: Kommando relativ zum config-dir + args; zu lang → `…/script.sh args`, dann auf 80 gekürzt.
- Spec-Nachtrag ohne ```` ```yaml ````-Block (der Loader-Test erwartet genau 7 YAML-Blöcke in der Spec).
