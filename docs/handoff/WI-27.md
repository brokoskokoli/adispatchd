## Bewusste Entscheidungen / Abweichungen

- **Projektfelder strikt mit der gewählten Identity** (`exactIdentity`), auch wenn die Source ein `project.identity` hat –
  sonst könnte ein Admin über eine freigeschaltete App indirekt als eine nicht freigeschaltete (z. B. PAT-)Identity
  schreiben. Folge: user-eigene Projekte (nur per Token lesbar) sind aus der UI nur mit einer freigeschalteten
  `github_token`-Identity änderbar. Metadaten/Optionen fürs Panel liest die Projekt-Lese-Identity.
- **`ui_actions` auch für `github_token`** erlaubt (Admin-Entscheidung; dann handelt man als der Token-Benutzer).
- **Fälschbarkeitsprüfung:** seit der Review-Runde ist `isIdentityForgeableLocally()` selbst verschärft (siehe unten).
- **GET-Routen `admin`:** Item-Details, Resolve und Audit-Liste sind `admin` (roles.test erlaubt das ausdrücklich für diese
  drei GETs). `GET /api/v1/ui-actions` braucht keine echte Anmeldung (lesend), `/items/*` schon.
- **Audit ab Identity-Prüfung:** Body-/Feldvalidierungsfehler (400, auch `comment_contains_secret`, `duplicate_comment`,
  Rate-Limit) und Rollen-/Login-Fehler (401/403 im Hook, stehen im `api write`-Log) werden nicht in `ui_actions`
  geschrieben; nicht freigeschaltete Identity, unbekannte Source/Item, `label_not_found` und alle GitHub-Fehler schon.
  Gespeichert: Labels/Feldwerte (maskiert) bzw. bei Kommentaren nur die Länge, nie der Text.
- **Vorschau als reiner Text** (keine Markdown-Darstellung); HTML-Kommentare erscheinen auf GitHub als Text (`&lt;!--`). Bestätigungsdialog nennt Identity-ID + Typ statt
  `<app-slug>[bot]` (Slug ist ohne zusätzlichen `GET /app`-Aufruf nicht bekannt).
- **GitHub-401/403 → 502**, damit die UI sie nicht mit eigener Anmeldung/Rolle verwechselt.

## Offene Punkte

- Gegen echtes GitHub nicht geprüft (nur Fake-GitHub): insbesondere die genaue Antwort auf gesperrte Unterhaltungen
  (wird als 403 → `github_forbidden` oder 422 → `github_rejected` gemeldet, Text von GitHub enthalten).
- Kein Browser-E2E im Gate; UI über DOM-freie Bausteine + einmal manuell im Browser.
- Repo-Labels: max. `maxPages` × 100 (Pagination-Limit der HTTP-Klasse); Labels werden bei jedem Panel-Aufruf gelesen.
- Keine Pagination/Filter für die Audit-Seite in der UI (zeigt die letzten 200; API kann `offset`).
