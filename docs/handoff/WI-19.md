## Fake-Engine (`src/executors/testing/fake-engine.ts`)
Node-Skript als `docker`/`podman` in einem Temp-Verzeichnis (Pfad über `ContainerEngineClient({ binaries })`). Protokolliert
jeden Aufruf (argv + komplette Prozessumgebung) in `calls.jsonl`; `run` parst die Flags, führt das Container-Kommando auf
dem Host aus und übersetzt Container-Pfade (env-Werte, Argumente, Workdir) über die Mounts auf Host-Pfade – der Worker
schreibt so in das gemountete Ausgabeverzeichnis. `stop`/`ps --filter label=…`/`rm -f`/`--version`, `fail(mode)` simuliert
einen nicht erreichbaren Daemon, `orphan(name, labels)` einen verwaisten Container.

## Bewusste Entscheidungen / Abweichungen
- **`user` Default = UID:GID des Dienstes** (WI nennt keinen Default): mit `--cap-drop ALL` kann root im Container auf
  Linux die `0600`-Kontext-/Token-Dateien und dienst-eigene Workspaces sonst nicht lesen/schreiben, und Dateien im
  Workspace gehören dem Dienst (Cleanup). Podman: bei gesetztem `user` (also praktisch immer) `--userns keep-id`.
- **`mounts[].mode` ist Pflicht** (kein stiller Default `ro`/`rw`).
- **`--cap-drop ALL`** (großgeschrieben, wie in der Docker-Doku; gleichbedeutend mit `all`), Mounts als `--mount type=bind,…`
  (deshalb keine `,`/`"` in Pfaden), `--workdir` statt `-w`, `--pull` wird immer gesetzt.
- **Kontextdatei als Einzeldatei-Mount**, Token-Dateien als Verzeichnis-Mount (atomarer Ersatz per `rename` bleibt sichtbar).
- **Engine-Fehler** (`docker run` Exit 125, z. B. Image fehlt) → `crashed` (Klassifikation unverändert nach Exit-Code);
  fehlendes Binary → `start_error`.
- **Recovery** stoppt *alle* Container der Instanz auf den Engines der Konfiguration/aktiven Runs; ohne Container-Workflows
  wird keine Engine aufgerufen. Ein Container-Run in `starting` ohne `run.spawn` wird bei Engine-Ausfall nicht
  `recovery_pending` (es kann kein Container existieren).
- API: `execute.command/args` eines Container-Workflows sind der Engine-Aufruf (bestehende Felder, UI unverändert nutzbar).
