Branch `wi-01-foundation`. Gate: `npm install && npm run check` grün (9 Testdateien, 104 Tests).

## Umgesetzt

- **Projekt:** `package.json` (ESM, `bin: agent-orchestrator → dist/cli/main.js`, Scripts `build`, `check`,

### `types.ts` im Detail
- **Status:** `TECHNICAL_STATUSES`/`TechnicalStatus` (inkl. `recovery_pending`), `TERMINAL_STATUSES`,
  `ACTIVE_STATUSES` (halten Lock, zählen zur Auslastung – inkl. `recovery_pending`),
  `TECHNICAL_FAILURE_STATUSES`, `isTerminalStatus`, `isTechnicalFailure`,
  **`RUN_STATUS_TRANSITIONS` + `canTransition`** (Referenz-Zustandsmaschine, die WI-03 durchsetzen soll),
  `BusinessResult`, `TriggerType`, `HOOK_NAMES`/`HookName`, **`hookForOutcome(status, result)`**,
  `ActionType`, `ActionStatus`, `LifecycleStatus`, `NOTIFICATION_EVENT_TYPES`, `Notifier`.
- **Filter:** `TriValue`, `FILTER_OPERATORS`/`FilterOperator`, `FilterValue`, `FilterNode`
  (`FilterAll|FilterAny|FilterNot|FilterPredicate`) + Type-Guards.
- **Felder:** `FieldType`, `FieldValue` (Datumswerte = ISO-Strings), `FieldDefinition { name, type,
  description?, link?, operators, expensive?, pushdown? }`, `FieldResolution = {known:true, value} |
  {known:false, reason}`.
- **Sources:** `SourceItem { sourceId, itemId, key, url, type, createdAt?, fields }` – `fields` ist nach
  **vollem Feldnamen** (auch gepunktet, z. B. `dependencies.blocked_by_open`) flach indiziert; teure Felder
  fehlen dort, bis sie per `resolveField` geholt werden. `SourceAdapter` (je konfigurierter Source eine
  Instanz): `type`, `sourceId`, `repository?`, `fieldDefinitions()`, `listCandidates({filter?, signal?})`

  `known:false`, nicht werfen), `applyUpdate(item, update, identity)`, `postComment(item, body, marker,
  identity) → CommentRef`, `findCommentByMarker(...) → CommentRef|null`. `SourceAdapterFactory` +
  `SourceAdapterDeps { credentials, logger, clock, fetch? }`.
- **Identities:** `IdentityRef` (= Identity-ID-String), `AccessToken { token, expiresAt }`,
  `CredentialProvider { getToken(identity), invalidate?(identity) }`.
- **Executor:** `ExecutionSpec` (command + args-Liste, `workingDirectory` bereits gerendert/geprüft,

- **Sonstiges:** `FetchLike` (injizierbares `fetch`), `Unsubscribe`.

### Template-Engine – Regeln
- Syntax `{name}`, `{{`/`}}` = Literal. Unbekannter Platzhalter ist **immer** ein Fehler, auch wenn ein Wert existiert.
- Gruppen/Scope (`TemplateScope`): `always` (`workflow.id`, `workflow.name`, `workspace.base_dir`,
  `timestamp`), `run` (`run.id`, `run.trigger`, `run.started_at`), `workspace` (`workspace.path`),
  `source` (`source.id|type|repository`, `item.id|number|key|url|title`), `result`
  (`result.status|result|message`), `parameters` (`{parameters.<name>}`, nur deklarierte Namen).
  WI-02 wählt den Scope je Config-Feld (z. B. `working_directory`: `{run:true, source:<sourcegebunden>}`,
  Kommentar in `on_success`: zusätzlich `result:true, workspace:true`).
- Modus `path`: jeder Wert → genau ein Segment (`sanitizeSegment`: alles außer `[A-Za-z0-9._@+=,-]` → `_`,
  nur-Punkte → `_`, leer → `_`, max. 128 Zeichen); `workspace.base_dir`/`workspace.path` sind vertrauenswürdige
  absolute Wurzeln, nur ganz am Anfang erlaubt; fehlender Wert = Fehler; NUL = Fehler; Ergebnis normalisiert.
  Der Aufrufer prüft das Ergebnis zusätzlich mit `resolveWithin(base_dir, …)`.
- Modus `text`: Werte unverändert, fehlende Werte → leer (umschaltbar mit `missing: 'error'`).

## Bewusste Entscheidungen / Abweichungen

- **`sourceItemKey` = `<sourceId>:<itemId>`** (wie in WI-01 gefordert). WI-06 nennt `github:<owner>/<repo>#<n>`
  als Key – bitte stattdessen `itemId` = Issue-/PR-Nummer als String und `key = sourceItemKey(sourceId, itemId)`
  setzen; eine owner/repo-Referenz kann als Feld (`repository`) bzw. `SourceAdapter.repository` geführt werden.
  Folge: Benennt man eine Source-ID um, verliert die Run-Historie die Zuordnung (dokumentieren in WI-12).
- **`Timers`-Abstraktion** zusätzlich zu `Clock` (WI-07 verlangt testbare Delays ohne echtes Warten).
- **Zusätzliche Module** `errors.ts` und `worker-protocol.ts`: gemeinsame Fehlerklassen und das
  Result-Schema sind Verträge zwischen mehreren WIs (Executor, Lifecycle, API/UI) – daher in core. WI-05
  verwendet `parseWorkerResult`/`ORCH_ENV`/`ORCH_EVENT_PREFIX` von hier statt eigener Kopien.
- **Größeneinheiten binär:** `100MB` = 100 × 1024² Bytes.
- **Dauern:** nur `<zahl><einheit>` (Dezimalzahlen erlaubt, müssen ganze ms ergeben); kein `1h30m`, keine
  nackte Zahl. `never` (Retention) behandelt WI-02 selbst.
- **Run-ID** enthält Millisekunden + 32 Zufallsbits; Sortierung chronologisch auf ms-Ebene.
- **Zustandsmaschine:** Hooks des Endergebnisses laufen im Zustand `finalizing`; Zielstatus wird vor
  `finalizing` festgelegt und persistiert (WI-03/08). `completed` ist nur aus `finalizing` erreichbar.
- **CLI-Exit-Code 70** für noch nicht implementierte Kommandos.
- TypeScript 7 / Vitest 5 / zod 4 sind die aktuell installierten Versionen (Pinning laut §24.6 vor Release).

## Offene Punkte

- `npm install` meldet, dass das `esbuild`-postinstall-Skript nicht über `allowScripts` freigegeben ist;
  `tsx` und `vitest` funktionieren trotzdem (Plattform-Binary `@esbuild/darwin-arm64` vorhanden). Unter Linux
  ggf. prüfen bzw. `npm install-scripts approve esbuild`.
- `SecretRedactor` ist best-effort (§24.8): transformierte Secrets (base64, gesplittet über Chunks) werden
  nicht erkannt; Stream-Redaction über Chunk-Grenzen ist Aufgabe von WI-05.
- Lock-Schlüssel für sourcefreie Runs (Cron/Manual) legt WI-03 fest (kein Helper in core).
