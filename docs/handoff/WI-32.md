## Bewusste Entscheidungen / Abweichungen

- **API-Form:** `GET /api/v1/dashboard` liefert `{title, columns: [{width, widgets}]}` statt `row`/`column` – jede Reihe
  hat damit einheitlich Spalten (ein Widget direkt in der Reihe = Spalte mit einem Widget). `refresh` heißt dort
  `refreshMs`. Zusätzlich `configured` (Layout aus der Datei oder Standard).
- **View-Requests:** `sections` als wiederholbarer Query-Parameter (Abschnitts-Titel dürfen Kommas enthalten). Mehrere
  Widgets einer View teilen sich im Client **eine** Abfrage (Vereinigung der Abschnitte, größtes `limit`); jedes Widget
  kürzt danach selbst. Die View-Widgets folgen keinen SSE-Ereignissen (wie die View-Seite), nur ihrem `refresh`.
- **Reiter-URL:** Pfad aus Reiter-IDs (`a/b`), mehrere Reiter-Widgets kommagetrennt. Damit das eindeutig ist, müssen
  Reiter-IDs unter allen `tabs`-Widgets **desselben Layouts** eindeutig sein (Validierungsfehler mit Hinweis auf `id`);
  in verschiedenen (verschachtelten) Layouts dürfen sie sich wiederholen. Reihenfolge der Auswahl: URL → `localStorage`
  → `default`; beim Zurück-Knopf gilt nur URL → `default` (sonst würde „Zurück“ den gemerkten Reiter zeigen).
- **Grenzen, die die WI offen ließ:** höchstens 20 Widgets je Spalte; die 100-Widget-Grenze zählt `tabs` selbst mit.
- **`width` an Widgets in einer Spalte** ist ein Fehler (nur Spalten bzw. Widgets direkt in der Reihe).
- **Hinweise** (Drain, nicht bereit, ungeschützte Bindung) stehen jetzt direkt unter der Überschrift, also über der
  Ressourcenleiste (in 0.7.0 zwischen Info-Kacheln und Scheduler) – „immer oben“ laut WI.
- **Spalten-Umbruch:** Das Standard-Layout nutzt feste Spalten (Scheduler/Capacity/Attention je ⅓) statt des früheren
  `auto-fit` (340 px); unter 900 px untereinander. Zwischen 900 und ~1100 px sind die drei Karten daher etwas schmaler
  als in 0.7.0.
- **`info` ohne `dashboard.yaml`** (nur im Standard-Layout möglich) bleibt verborgen; leere Spalten/Reihen blendet CSS
  (`:has`) aus.
- **Ein `tabs`-Widget** ist keine Karte: Überschrift (falls `title`), Reiterleiste, darunter das Layout des Reiters.
- **Gate vor dem ersten Commit:** wegen des langsamen Rechners nur Typecheck + gezielte Tests; das volle Gate lief am
  Ende auf dem fertigen Stand.

## Review-Nacharbeit (Runde 1)

1. **`resources_full` mit `title`:** `serverSection({ title })`; `render()` baut die Überschrift aus dieser Option
   statt fest „Server“ (Quelltext-Test in `ui/shared/nav.test.ts`, im Browser geprüft).
2. **Sortierung im View-Widget:** Der Server kürzt nach `limit` (bewusst, damit nicht alle Zeilen übertragen werden);
   „erst sortieren, dann kürzen“ ginge nur mit allen Zeilen im Client. Stattdessen steht unter jeder gekürzten Tabelle
   „First N of M rows in the configured order; column sort and group counts cover these only.“ mit dem Link
   „… more“.
3. **Hintergrund-Tab:** View-Polling pausiert bei `document.hidden`; ausgelassene Abrufe werden bei
   `visibilitychange` sofort nachgeholt. Andere Daten des Dashboards kommen per SSE (kein Polling).
4. **„N more …“** verspricht höchstens so viele Zeilen, wie die View-Seite zeigt (`MAX_VIEW_ROWS` = 2000, im UI
   gespiegelt, ein Test prüft die Gleichheit mit dem Server-Wert).
5. **Pfeiltasten** in der Reiterleiste ersetzen den History-Eintrag (`replaceState`), Klicks legen einen neuen an.
6. **„did you mean“ bei Vertauschungen:** `editDistance` rechnet jetzt Optimal String Alignment (Vertauschung zweier
   Nachbarzeichen = 1), z. B. `titel` → `title`, `widht` → `width`. Gilt für alle Schlüssel-/Feldvorschläge der
   Konfiguration; bestehende Tests unverändert grün.
7. **Referenzfehler trotz Schemafehler:** Scheitert das Schema eines Widgets, werden lesbare `view`/`sections`/`ids`/
   `workflows` trotzdem gegen die Konfiguration geprüft (Test in `config/dashboard-layout.test.ts`).
8. `docs/api.md`: Leerzeile vor „Dashboard-Layout“.
