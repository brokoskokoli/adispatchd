### Ablauf `startRun(run, {verifyItem?})`
Jede Transition wird persistiert, bevor weitergearbeitet wird.
1. Run muss `reserved` sein (Snapshot liegt seit `reserve` in `runs.config_snapshot`; ungültiger Snapshot → `start_error` ohne Hooks).
2. **Item neu lesen** (§7) über `adapter.getItem` (bei `source_item_key`, also auch manuelle Runs mit Item); Event `run.item_reread`.
   - Item weg → `cancelled` („item no longer available“), `verifyItem(item) === false` → `cancelled` („item no longer matches the workflow“):
     **ohne Hooks, ohne Zählung** (Rennen verloren, nichts wurde am Item verändert).
   - Lesefehler/Adapter fehlt → `start_error` (zählt, **ohne** Hooks – `on_start` lief nie).
3. `reserved → starting`, dann `on_start` (`runHook`, `wait: true`, Signal = Cancel ∪ Stop).
   - Kette `failed` → **Worker wird nicht gestartet**, Rest der `on_start`-Kette wird verworfen (`abandonHook`, pending → skipped;
     die gescheiterte Action bleibt `failed`/sichtbar), Ziel `start_error` („on_start action '<id>' failed“) → `on_start_error`.
   - `interrupted`/Cancel → Rest verwerfen → `cancelled` → `on_cancel`.
4. Workspace/Kontext/Secrets (`buildExecutionSpec`), Fehler → `start_error` + `on_start_error`.
5. Vor dem Spawn: `workspace_path`, `command` und Event **`run.spawn`** persistieren (Recovery weiß dann, dass ein Prozess existieren kann).
6. `executor.start` → sofort `starting → running` mit `pid` **und** `process_start_identity` in einer Transition. Listener:
   `onOutput` → Bus `run.output` (nicht persistiert), `onEvent` → `appendWorkerEvent` (setzt `status_message`), `onDiagnostic` → `appendDiagnostic`.
7. `classifyOutcome` (§8.2) → `beginFinalization(target, {update:{exitCode, result, error}, blockPolicy:{maxTechnicalFailures aus Snapshot}})`
   – Zähler + ggf. Block **in derselben Transaktion** wie `→ finalizing`; nach Commit Bus `block.created` + Notification `retry_block_created`
   (Payload: `blockId, workflowId, itemKey, reason, failureCount, runId, sourceUrl, affectedRunIds`). **Erst danach** der Hook.
8. Completion-Hook `hookForOutcome(...)` aus dem **Snapshot** (`runHook`, `wait: true`, Signal = Stop). Hook `interrupted` (forcierter Stop)
   → Run bleibt `finalizing` (Recovery setzt fort). Hook `failed` → Run wird trotzdem beendet, `lifecycle_status = failed` bleibt sichtbar.
9. Workspace-Cleanup gemäß Snapshot `workspace.cleanup` (`always|on_success|never`), Event `workspace.cleanup`; dann `finish` (Lock frei).

Hooks mit leerer Action-Liste werden nicht aufgerufen (sonst bliebe `lifecycle_status = running` stehen, da WI-07 ohne Journal nicht aggregiert).

### Retry-Blocks (§11)
Zählung/Block komplett in `RunRepository.beginFinalization` (WI-03): `crashed|start_error|timed_out` +1, `completed/success` → 0,
`failure`/`cancelled` unverändert. Block wird bei Erreichen von `retry.max_technical_failures` (Snapshot) angelegt, bevor irgendein Hook
läuft – ein `on_crash`, das `ready-for-coding` zurücksetzt, kann keinen Neustart auslösen (Scheduler reserviert mit `failIfBlocked`).
`clearBlock(id, by)` → neue Zählperiode, Historie bleibt, Bus `block.cleared`.

### Cancel (§13)
`cancelRun(id, {reason})`: `reserved|starting|running → cancelling` + Event `run.cancel_requested` (persistiert vor allem anderen),
Abbruch-Signal (Item-Lesen, `on_start`, Secret-Auflösung), dann `proc.cancel()` (SIGTERM → `cancel_grace` → SIGKILL → Ende bestätigt).
Ergebnis `cancelled` (Grund = `reason`) → `on_cancel` → `cancelled`. Kein Zähler. **Misslingt das Beenden** (`kill_failed`): Run bleibt
`cancelling`, `error = {code:'kill_failed'}`, Event `run.cancel_failed`, `cancelRun` rejected mit `kill_failed`; erneuter Aufruf versucht es
wieder; endet die Gruppe später doch, läuft der Run normal zu `cancelled` weiter. Ein reservierter, nie gestarteter Run wird direkt
`cancelled` (ohne Hooks). `finalizing`/`recovery_pending` → `run_not_cancellable`.

### Recovery (§14, Variante A) – `recover()`
Vor dem Scheduler aufrufen; `ready` wird **erst am Ende** gesetzt (Bus `system.status` mit `ready: true` nach allen Finalisierungen/Hooks).
Alle aktiven Runs parallel (pro Run sequenziell):

| Zustand in DB | Vorgehen |
|---|---|
| `reserved` | `cancelled` ohne Hooks, ohne Zählung (nie gestartet) |
| `finalizing` | laufende Actions sicher machen (WI-07 `resumeIncomplete`), Rest von `on_start` verwerfen, Completion-Hook aus persistiertem Ziel fortsetzen (`runHook` idempotent), Cleanup, `finish` – Zähler wurde bereits beim ursprünglichen `→ finalizing` angewendet (genau einmal) |
| `starting`/`running`/`cancelling`/`recovery_pending` | Prozessprüfung (s. u.); weg → Actions sicher machen, `on_start`-Rest verwerfen, Ziel `crashed` (bzw. `cancelled`, wenn der Run `cancelling` war) mit `on_crash`/`on_cancel`; nicht verifizierbar → `recovery_pending` |

Prozessprüfung (`terminateProcessGroupIfSame`, Grace = Snapshot `cancel_grace`, überschreibbar):
- `terminated`/`gone` → weg (`crashed`).
- `not_same` (PID gehört anderem Prozess) → nur „weg“, wenn **keine** Prozessgruppe mit der alten PGID existiert; sonst `recovery_pending`
  (Akzeptanzkriterium „falsche Identität wird nicht getötet → recovery_pending“; nach einem Reboot mit PID-Reuse ohne Gruppen-Kollision
  wird korrekt `crashed`).
- `group_alive_unverifiable`, `unknown`, `kill_failed` → `recovery_pending`.
- PID ohne Identität → Gruppe existiert ? `recovery_pending` : `crashed`; keine PID, aber `run.spawn`-Event → `recovery_pending`
  („spawned, pid not persisted“); kein Spawn → kein Prozess (`crashed` mit `on_crash`, sofern `starting` erreicht war).

`recovery_pending`: Transition mit `error = {code:'recovery_failed', message, previousStatus, pid, at}`, Event `recovery.failed`,
Notification `recovery_failed` **nur beim ersten Eintritt** (Payload `runId, workflowId, sourceItemKey, sourceUrl, pid, previousStatus, reason`).
Lock bleibt → kein Doppelstart. Auflösung: `retryRecovery(id)` (prüft erneut, z. B. nachdem der Operator den Prozess beendet hat) oder
`retryRecovery(id, {assumeGone: true})` (Operator bestätigt; es wird nichts signalisiert). `retryRecovery` setzt auch einen
**unbeaufsichtigten `finalizing`-Run** fort (z. B. nach internem Fehler) und wirft `run_controller_not_ready` während der Recovery bzw.
`run_controller_not_accepting` beim Drain/Stop. Jeder Run in Recovery ist in `active` registriert (`kind: 'recovery'`): Drain wartet,
Cancel wird mit `run_not_cancellable` abgelehnt, keine Doppelbearbeitung. Danach: beendete Runs mit unvollständigen
Action-Ketten (`runIdsWithIncompleteActions`) per `resumeIncomplete` fortsetzen (`on_start` wird dabei nie fortgesetzt, nur verworfen).
`RecoveryReport {finalized, pending, resumedActions, errors}`.

### Shutdown (§14)
- `pause()/resume()`: nur Flag; `canStartAutomatically()` false, `canStartManually()` bleibt true; laufende Runs unberührt.
- `drain()`: keine neuen Runs (auch manuell: `startRun` wirft `run_controller_not_accepting` **und finalisiert den übergebenen
  reservierten Run als `cancelled`**, damit kein Lock hängen bleibt), wartet auf alle aktiven Runs, dann `onStop`.
- `cancelAllAndShutdown(reason?)`: `cancelRun` für alle aktiven Runs (`on_cancel` läuft), warten, dann `onStop`.
- `shutdown({mode, drainTimeoutMs, cancelTimeoutMs, reason})`: Drain mit Timeout → danach Cancel-All → nach `cancelTimeoutMs`
  werden laufende Hooks per Signal unterbrochen (Actions → `pending`, Run bleibt `finalizing`/`cancelling`; Recovery setzt beim nächsten
  Start fort), max. `abortSettleMs` (10 s) warten, dann `onStop`. Ergebnis `{outcome: 'drained'|'cancelled', leftActive}`.
- **Eskalation:** weitere Aufrufe liefern dasselbe Promise, verschärfen aber einen laufenden Shutdown: `mode: 'cancel'` macht aus einem
  Drain sofort Cancel-All (`drain()` → `cancelAllAndShutdown()`, „zweites SIGTERM“); kleinere `drainTimeoutMs`/`cancelTimeoutMs` (ab dem
  späteren Aufruf gezählt) ersetzen größere (API-Drain ohne Limit, danach SIGTERM mit Timeouts). Wartephasen werden dafür sofort geweckt.
- Ein laufendes `recover()` wird vor dem Stoppen abgewartet (`onStop` erst danach).

### SIGTERM / systemd (für WI-10/WI-12)
Empfehlung SIGTERM-Handler (WI-10): `await controller.shutdown({ mode: 'drain', drainTimeoutMs: D, cancelTimeoutMs: C })`, danach
Scheduler/HTTP stoppen, DB schließen, Instanz-Lock freigeben, **Exit-Code 0**.
- `KillMode=mixed`: SIGTERM nur an den Hauptprozess. Mit dem Default `control-group` bekämen auch alle Worker (gleiche cgroup, trotz eigener
  Prozessgruppe) sofort SIGTERM → Drain wäre unmöglich, Runs würden `crashed`.
- `TimeoutStopSec` > `D + C + max(cancel_grace) + Puffer` (Beispiel: `D = 10min`, `C = 2min`, `TimeoutStopSec=15min`). Läuft er ab,
  SIGKILLt systemd die ganze cgroup inkl. Worker; beim nächsten Start findet die Recovery die Gruppen weg → `crashed` + `on_crash`
  (zählt). Lange Agent-Runs (Stunden) können daher bei `systemctl stop` nie vollständig gedraint werden – für geplante Abschaltungen
  vorher per CLI/API `drain` auslösen und abwarten (§14 „ein sofortiger Kill kann keinen Drain garantieren“).
- `Restart=on-failure`: nach geordnetem Shutdown (Exit 0) kein Neustart; ein Crash (≠ 0/Signal) startet neu → Recovery.
- Bei SIGINT (lokal) gleiches Verhalten; ein zweites SIGTERM/SIGINT ruft `shutdown({ mode: 'cancel' })` (Eskalation, s. o.).
- Hinweis: Stürzt unter systemd der **Hauptprozess** ab, beendet systemd (je nach `KillMode`, bei `mixed`/`control-group` per SIGKILL an die
  cgroup) auch die Worker. Verwaiste, noch lebende Worker (Recovery Variante A: verifizieren + beenden) entstehen daher v. a. **außerhalb
  von systemd** (lokal, `npx`, `KillMode=process`/`none`); unter systemd findet die Recovery die Gruppen i. d. R. bereits weg → `crashed`.

## Event-Bus (WI-10 SSE)

```ts
type BusEvent =
  | { type: 'run.event'; event: RunEventRecord }      // persistiert; event.id = SSE-ID (Last-Event-ID → events.listSince)
  | { type: 'run.output'; runId; stream: 'stdout'|'stderr'; data; at }   // live, nicht persistiert, bereits redigiert
  | { type: 'run.action'; action: RunActionRecord }    // Journal-Änderung (nach Commit)
  | { type: 'block.created' | 'block.cleared'; block: BlockRecord }
  | { type: 'system.status'; status: { ready, paused, draining, stopping, activeRuns } };
bus.subscribe(listener, types?) → Unsubscribe        // Listener synchron, Exceptions werden geloggt; Listener müssen sofort zurückkehren
```
- Alle persistierten `run_events` (Status-Transitionen `run.status` inkl. `target`/`blockId`, Worker-Events, Diagnosen, `lifecycle.*`,
  Controller-Events) erscheinen als `run.event` **nur nach Commit, in ID-Reihenfolge, genau einmal** (`PersistedEventPublisher`
  startet bei `events.latestId()`; Historie liefert SSE aus der DB nach).
- Verdrahtung: **ein** Publisher pro Prozess, den Controller und LifecycleEngine teilen:
  ```ts
  const bus = new RunEventBus(logger);
  const publisher = new PersistedEventPublisher(persistence, bus);
  const lifecycle = new LifecycleEngine({ ..., notifier, onActionChange: publisher.actionListener() });
  const controller = new RunController({ repositories: persistence, lifecycle, sources, dataDir, publisher, credentials,
    notifier, maxLogBytesPerRun: () => config.current.global.retention.maxLogSizePerRunBytes, logger, onStop });
  ```
- Controller-Event-Typen (`RUN_EVENTS`): `run.spawn`, `run.item_reread`, `run.cancel_requested`, `run.cancel_failed`, `run.hook_error`,
  `run.controller_error`, `recovery.failed`, `recovery.recovered`, `workspace.cleanup`.

## Bewusste Entscheidungen
- **`on_start` scheitert → `start_error`, Worker startet nicht** (Spec §8.2 „Prozess konnte nicht gestartet werden“): das Item wurde nicht
  (vollständig) beansprucht; Fortsetzen würde ohne Label-Übergang arbeiten. `start_error` zählt technisch (§11) und `on_start_error`
  macht Teiländerungen von `on_start` rückgängig. Der Rest der `on_start`-Kette wird verworfen (sonst würde ein späteres manuelles „Skip“
  der gescheiterten Action – WI-07 setzt die Kette dann fort – Start-Labels an einem beendeten Run anwenden).
- **Completion-Hooks laufen nur, wenn der Run `starting` erreicht hat** (WI-01-Frage „on_cancel ohne on_start“): Vor `starting` wurde
  nichts am Item verändert → keine Hooks. Ermittelt aus dem persistierten `run.status`-Event (auch in der Recovery).
- **Rennen verloren / Item weg → `cancelled`** statt `start_error`: kein technischer Fehler, darf nicht zum Block führen.
- **Recovery: `reserved` → `cancelled`** (nicht `crashed`): ein Controller-Neustart vor dem Start ist kein Fehler des Workers.
- **Recovery: `not_same` mit existierender PGID → `recovery_pending`** (siehe oben); Notification nur beim ersten Eintritt.
- **Recovery wartet auf die Hooks** (auch Retry-Delays), bevor `ready` gesetzt wird (AC „Ready erst danach“). Lange GitHub-Ausfälle
  verzögern damit den Scheduler-Start – bewusst zugunsten der Konsistenz.
- **Workspace außerhalb `base_dir`** (absolutes `working_directory`, von WI-02 erlaubt) wird ohne Basis-Guard angelegt und **nie gelöscht**;
  `working_directory == base_dir` → `start_error`.
- **Unerwartete interne Fehler** während der Überwachung (z. B. DB-Fehler): Event `run.controller_error`; der Run wird – wo die
  Zustandsmaschine es erlaubt – `recovery_pending` (Fehler + `recovery_failed`-Notification, Lock bleibt), ein `finalizing`-Run bleibt
  `finalizing`. Der Eintrag bleibt beaufsichtigt, bis ein gestarteter Worker beendet ist (Drain wartet); danach `retryRecovery`.
  Kein voreiliges Finalisieren bei evtl. laufendem Prozess.
- `block.created` wird nach dem zugehörigen `run.status`-Event (`→ finalizing` mit `blockId`) publiziert.
- Prozessgruppen-Prüfung der Recovery ist injizierbar (`groupExists`, neben `processInspector`/`kill`).
- Executor pro Run (`createExecutor({workspaceBaseDir})`, Default `ShellExecutor` mit realen Timern); Log-Limit über `maxLogBytesPerRun`
  (Getter, da `retention` nicht im Snapshot liegt).
