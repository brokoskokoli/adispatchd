## Bewusste Entscheidungen / Abweichungen

- **Zusätzlicher Schlüssel `auth.trusted_proxies`** (Default `[127.0.0.1, ::1]`) für den Passwort-Modus: Das WI verlangt
  `Secure` bei `X-Forwarded-Proto: https` „von einem vertrauenswürdigen Proxy“, nennt aber nur
  `trusted_header.trusted_proxies`. Dieselbe Liste regelt dort `X-Forwarded-For` für das IP-Rate-Limit (letzter Hop).
- **Hash-Format ohne `$`** (`scrypt:N:r:p:salt:hash`), damit es in Env-Dateien/Shells nicht expandiert wird.
- **Sessions:** feste Gültigkeit ab Login (keine gleitende Verlängerung); Rolle wird bei jeder Anfrage aus der aktiven
  Konfiguration gelesen (Reload wirkt sofort, entfernte Benutzer sind abgemeldet). `auth` insgesamt ist reload-fähig.
- **`read_requires_login: false`** gilt nur für `GET`/`HEAD`; auch Dry-Run und `config/validate` (POST, Rolle `viewer`)
  brauchen dann eine Anmeldung.
- **`/ready`** liefert ohne Anmeldung nur `{ready}` (Status 200/503 unverändert); `/health` unverändert.
- **Unbekannte `/api/`-Pfade** brauchen eine Anmeldung (401 statt 404), andere unbekannte Pfade bleiben 404 (UI).
- **Statische UI** (`GET /*`) ist öffentlich, damit die Login-Seite lädt; sie enthält keine Daten.
- **Steuer-Token** wird in allen Modi geschrieben (auch `none`), damit ein späterer Reload auf `password` die CLI nicht
  aussperrt; ausgewertet wird er nur bei `mode` ≠ `none`. Name im Audit: `control-token` (`via: control_token`).
  Grenze (dokumentiert): Worker desselben Dienstbenutzers können die Datei lesen – gleiche Vertrauensgrenze wie Spec §20.2.
- **Audit:** Log-Zeile `api write` für **jede** schreibende Anfrage eines angemeldeten Benutzers (Route, Status, nie
  Bodies); Run-bezogene Aktionen zusätzlich als Run-Event (`start`, `cancel`, `recovery_retry`, `action_retry`,
  `action_skip`) – in der UI bei den Events des Runs sichtbar; Blocks über `clearedBy`. Kein Audit bei `mode: none`
  (Verhalten unverändert). Eine eigene Audit-Tabelle bringt erst WI-27.
- **UI:** Buttons ohne Rolle werden deaktiviert (nicht ausgeblendet), der Tooltip nennt die fehlende Rolle; 403 einer
  Aktion erscheint als Toast. Nach Login/Logout lädt die Seite neu (frische SSE-Verbindung mit Cookie).
- **`GET /api/v1/system/metrics`** (WI-23, nach dem Merge) → `viewer`; `POST /api/v1/dashboard/info/:id/refresh` (WI-24)
  → `operator`.

## Offene Punkte

- Kein Browser-E2E im Gate (wie WI-11/25): Login-Ablauf in der UI nur über die DOM-freien Bausteine und einmal manuell
  (Login-Seite) geprüft; die angemeldete Ansicht mit deaktivierten Buttons wurde nicht im Browser angesehen.
- Sessions nur im Speicher (laut WI); kein „angemeldet bleiben“, kein Passwortwechsel in der UI (Hash in der Env-Datei).
- Kein Schutz gegen sehr viele parallele Login-Versuche über viele IPs hinaus (max. 8 gleichzeitige scrypt-Läufe →
  429); bei Bedarf Rate-Limit am Proxy.
- Linux/systemd: Pfad `/var/lib/adispatchd/control.token` und `sudo adispatch status --data-dir …` nicht auf Linux geprüft.
- WI-27: nutzt `ROUTE_ROLES` (`admin`-Einträge), `req.principal`/`actorOf` und `controller.recordUserAction`; eine
  dauerhafte Audit-Tabelle (`GET /api/v1/ui-actions`) kommt dort.
