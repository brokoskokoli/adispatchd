### Start-/Stop-Reihenfolge (`createApp` / `App`)
Lock (`acquireInstanceLock`) → `openPersistence` (Migration) → `ConfigManager.create` → `SourceRegistry` (ein gemeinsamer
`SecretRedactor` für Credentials, Logger, Notifications, Lifecycle) → Bus/Publisher/EventHub → Notifications → Lifecycle
(`onActionChange: publisher.actionListener()`) → RunController → Scheduler → Views → Retention → HTTP.
`start()`: listen (`/health` sofort, `/ready` 503) → `notifications.start()` → `controller.recover()` → `scheduler.start()`,
`retention.start()` → `ready` (`/ready` 200). Recovery-Fehler → Shutdown mit Exit 1.
`shutdown({mode, drainTimeoutMs, cancelTimeoutMs})`: `scheduler.stop()` → `controller.shutdown(...)` → Hintergrund-Operationen
(manuelle Retries) abbrechen (max. 10 s) → Retention/Notifications stoppen → SSE schließen → HTTP schließen → DB schließen →
Lock freigeben → `stopped` (`exitCode` 0 bzw. 1). Folgeaufrufe eskalieren (an `controller.shutdown` durchgereicht).
SIGTERM/SIGINT: 1. Drain mit `drainTimeoutMs` (Default 10 min), danach Cancel-All mit `cancelTimeoutMs` (2 min); 2. Signal
→ sofort Cancel-All; 3. Signal → `process.exit(1)` (Recovery räumt beim nächsten Start auf). API-Drain/Cancel-All beenden den
Prozess ebenfalls mit Exit 0 (CLI wartet auf `app.stopped`).

## Bewusste Entscheidungen
- `/health` sofort nach `listen`, `/ready` erst nach Recovery + Scheduler-Start und `false` ab Shutdown-Beginn.
- Host-Allowlist für alle Requests (DNS-Rebinding) + CSRF für mutierende: Pflicht-Header + JSON-only (kein text/plain-/Form-Parser)
  + `Origin` auf erlaubtem Host + `Sec-Fetch-Site`-Prüfung, keine CORS-Header, `OPTIONS` → 405.
- Hintergrund-Operationen (Action-Retry/Skip, Recovery-Retry) laufen fire-and-forget mit App-AbortSignal; Fehler, die
  synchron beim Start entstehen (Busy, falscher Status), werden noch als 4xx gemeldet.
- Run-Detail: `identity` = `runs.identity` ∨ Workflow-Identity ∨ Source-Identity aus dem Snapshot (Controller setzt
  `runs.identity` derzeit nicht); `input` = `runs/<id>/context.json` (vom Executor redigiert).
- Logs-Endpunkt in Bytes; UTF-8-sichere Schnitte; `logs.<stream>.truncated` aus `diagnostic.log_truncated`-Events im Detail.
- Views: nur `true` wird angezeigt (`unknown` gezählt in `filterUnknown`); Sortierung typbewusst, leere Werte zuletzt; max. 2000 Zeilen;
  `run.last_*` = letzter Run des Items nach Erstellzeit (workflowübergreifend, Spec §17). Link-Spalte fällt auf `FieldDefinition.link` zurück.
- Notifications: deaktivierte Eventtypen (`notifications.on`) werden nicht gespeichert; 4xx (außer 408/429) und fehlende
  Env-Variablen → sofort `failed`; Netzwerk/5xx/Timeout → Backoff 5 s, 30 s, 2 min, 10 min, 30 min (6 Versuche).
  Body mit `text` (Slack-kompatibel). Zustellung at-least-once (Abbruch beim Stop → bleibt `pending`).
- Retention: Zeilen zuerst löschen (Schutz in derselben Transaktion erneut geprüft), dann Dateien; verwaiste
  `runs/<id>`/`logs/<id>` ohne DB-Zeile ab 24 h Alter entfernt. Cleared Blocks nach `blocked_runs`, Notifications nach
  `failed_runs`, Cron-Firings nach `completed_runs` (Fallback 30 d). Erster Lauf 60 s nach Readiness.
- Bei Reload bleiben Adapter/Identities entfernter Sources erhalten (Runs mit altem Snapshot können ihre Hooks beenden);
  Neuaufbau nur, wenn sich Sources/Identities geändert haben.
