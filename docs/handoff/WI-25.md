## Bewusste Entscheidungen / Abweichungen

- **`embed` Default `false`** (WI nennt keinen Default): ein Link im neuen Tab funktioniert immer, Einbetten hängt vom Tool ab.
- **API:** `externalLinks` als zusätzliches Top-Level-Feld von `GET /api/v1/config` (bestehender Endpunkt, wie im WI
  vorgeschlagen). `config.global.ui` im selben Response enthält die vollständige Liste inkl. deaktivierter Einträge
  (Konfigurationsansicht); die UI nutzt nur `externalLinks`.
- **CSP als Header statt `<meta>`:** nötig, weil eine Meta-Policy statisch ist und zusätzlich zum Header gelten würde.
  Inhalt sonst unverändert (kein zusätzliches `frame-ancestors`; `X-Frame-Options: DENY` bleibt).
- **Ladefehler-Erkennung:** Bei Cross-Origin-Frames nicht zuverlässig möglich (`load` feuert auch bei Fehlerseiten,
  blockiertes Framing ist nicht auslesbar) → Link und Hinweistext sind **immer** sichtbar.
- **Nach Reload:** Server-CSP sofort aktuell; in einem bereits geöffneten Tab gilt die beim Laden erhaltene CSP – die
  Seite erkennt ein danach hinzugekommenes Origin und bietet „Reload page“ an.
- **Token-Heuristik:** Warnung für Parameternamen `t`, `key`, `auth`, `sig`, `signature`, `pass`, `pwd` (exakt) sowie alles
  mit `token`, `secret`, `passw`, `api_key`/`apikey`, `credential`.
- IPv6-Literale können in CSP-Host-Quellen nicht stehen → Warnung bei `embed: true`, kein `frame-src`-Eintrag.

## Offene Punkte

- Kein echter Browser-E2E-Test im Gate (wie WI-11); DOM-Logik über Fake-DOM getestet, einmal manuell in Chrome.
- Unterpfade hinter einem Reverse Proxy (`https://host/inspect/`) hängen vom Tool ab; die Doku empfiehlt einen eigenen Hostnamen.
- Merge mit WI-23/WI-24: `src/ui/client/app.ts` (Import-Block, Ende der Nav-Erzeugung, `pageFor`, `onMessage`, Startblock),
  `src/api/server.ts` (`onSend`-Hook, `/api/v1/config`), `CHANGELOG.md` (0.3.1-Abschnitt zusammenführen).
