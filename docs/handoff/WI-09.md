### Planungsschritt (Spec §7, Punkte 1–8)
1. **Gate:** Nur wenn `controller.canStartAutomatically()` (Recovery fertig, nicht pausiert, kein Drain/Stop); sonst
   wird der Schritt als `skipped: 'not_ready'|'paused'|'draining'` protokolliert, ohne zu pollen.
2. **Pollen** aller aktivierten Source-Workflows **parallel**; `listCandidates` mit dem Pushdown-Teil des Filters
   (pro Schritt je `(source, pushdown)` nur ein Aufruf). Fehler/fehlender Adapter → Diagnose `status: 'source_error'`
   nur für diesen Workflow, andere laufen weiter.
3. **Günstiger Filter zuerst:** Filter wird mit einer FieldSource ausgewertet, die teure Felder als `unknown` meldet
   (`cheapOnly`). Starke Kleene-Logik ist monoton → `false` ist endgültig (Kandidat fällt raus, Diagnose `filtered`),
   `true` endgültig; nur `unknown` braucht später die teuren Felder.
4. **Normalisieren** `(source, item, workflow)` (Duplikate einer Listing-Antwort fallen weg; verschiedene Workflows
   behandeln dasselbe Item getrennt).
5. **Prioritäten:** `resolveItemPriority` mit derselben memoisierenden FieldSource (ein Batch teurer Felder pro Item
   und Schritt), dann `sortCandidates` über **alle** Workflows (Workflow-Prio desc → Item-Prio desc → `createdAt` →
   Item-Key → Workflow-ID).
6. Pro Kandidat in dieser Reihenfolge: **freier Slot?** (früh, damit volle Limits keine API-Aufrufe/Checks kosten) →
   **Lock** (`activeRunForItem`) → **Block** → **Workflow-Conditions** (höchstens einmal pro Schritt und Workflow,
   zusätzlich TTL-Cache `cache`, Key `<wf>:condition:<i>`) → **teurer deklarativer Filter** (nur falls günstig
   `unknown`) → **Shell-Filter** → **Item-Conditions** (sequenziell, erster nicht-`true` entscheidet).
   `unknown` ist nie startfähig (`filter_unknown`, `shell_filter_unknown`, `condition_unknown`).
7. **Synchroner Abschnitt** (kein `await`): Gate, Workflow noch aktiv/unverändert (Hash), Limits mit **Live-Werten**
   (Overrides), dann `runs.reserve({…, failIfBlocked: true})` und sofort `controller.startRun(run, {verifyItem})`.
   `verifyItem` = günstiger Filter auf dem frisch gelesenen Item (`false` → Controller bricht ohne Hooks ab).
   Lock-/Block-Konflikte bei der Reservierung → `locked`/`blocked`.
8. Nicht startfähige Kandidaten werden übersprungen, der nächste wird geprüft. Keine persistente Kandidaten-Queue.
- Planungsschritte überlappen nie (`planOnce` ist serialisiert); der nächste Poll wird erst nach Ende des Schritts mit
  `scheduler.polling_interval` (live aus der Config) gestellt. Der erste Schritt läuft direkt bei `start()`.
- Auslastung = `runs.countActive()` (alle Trigger inkl. manuell und `recovery_pending`).

### Cron (Details: `docs/cron-semantics.md`)
- Pro Schedule-Workflow ein Timer (max. 1 h im Voraus, dann Neuberechnung); Behandlung pro Workflow serialisiert.
- Fällige Slots `(lastHandled, now]`: der jüngste innerhalb der Toleranz (`cronMisfireToleranceMs`, 60 s) wird
  entschieden, ältere → `skipped_missed`. Nach Neustart ab `cron_firings.latest` (Downtime-Slots → `skipped_missed`,
  nie nachgeholt). Entscheidung: deaktiviert → Gate → Limits → Block (Workflow-Scope) → Conditions → (erneut
  synchron prüfen) → Transaktion `cron_firings.record('started')` + `runs.reserve({triggerType:'schedule',
  scheduledFor, failIfBlocked:true})` + `run_id` → `startRun`.
- Reload: geänderter Ausdruck/Zeitzone → neu ab „jetzt“; entfernte Workflows → Timer weg; Shell-Check-Cache wird bei
  jedem Reload komplett invalidiert.

### Manueller Start
`startManual(workflowId, { itemRef?, parameters? })`:
- Source-Workflow: `itemRef` Pflicht → `adapter.parseItemRef` → `adapter.getItem`. Schedule/Manual-Workflow mit
  `itemRef` → Fehler. Parameter über `ConfigManager.validateParameters` (Defaults angewendet, gespeichert in
  `runs.parameters`, leer → `null`).
- Umgeht Filter, Conditions, Retry-Blocks, Prioritäten, Limits, `enabled` und Pause; **nicht** den Lock
  (`LockConflictError`, `lock_conflict`). Reservierung + `startRun` synchron nach der letzten Prüfung.
- Erfordert `controller.canStartManually()` (Recovery fertig, kein Drain/Stop).

### Dry-Run
`dryRun(workflowId)` / `dryRunWorkflow(deps, workflowId)`: Source-Abfrage, deklarativer Filter inkl. Dependencies
(teure Felder werden normal aufgelöst), Prioritäten, Locks/Blocks, Kapazität; Shell-Filter/Conditions **nie**
(`not_evaluated`); keine Reservierung, keine Actions. Unterschiede zum echten Schritt: Eignung wird vor der Kapazität
geprüft (jeder Kandidat zeigt seinen Filter-/Lock-/Block-Status), Kapazität wird danach in Prioritätsreihenfolge
simuliert (`pending_checks` belegt einen Slot); andere Workflows werden nicht simuliert. Schedule-Workflows:
nächste 5 Slots, Prognose für den nächsten Slot, letzte 10 `cron_firings`, Block.

### CLI `workflow dry-run <id> --config-dir <dir> [--data-dir <dir>] [--json]`
Lokal, ohne laufenden Server: Config laden, GitHub-App-Credentials aus Env, Adapter je Source; Datenbank
`<data-dir>/orchestrator.sqlite` wird **read-only** geöffnet (funktioniert auch bei laufender Instanz im WAL-Modus,
Schemaversion muss passen; sonst Hinweis und leerer Zustand). Exit 0 = ok, 1 = Config ungültig / unbekannter
Workflow / Source-Fehler (Ergebnis wird trotzdem ausgegeben), 2 = `--config-dir` fehlt. HTTP-Variante gegen laufende
Instanz: WI-12.

## API für WI-10

```ts
import { Scheduler, SchedulerError, formatDryRun, type SchedulerRunController } from './scheduler/index.js';

const scheduler = new Scheduler({
  config,                 // ConfigManager (effektive Werte inkl. Overrides)
  repositories: persistence,
  controller,             // RunController (erfüllt SchedulerRunController strukturell)
  sources: (id) => adapters.get(id),
  shellChecks?,           // ShellCheckRunner (Default: eigener, Cache-TTL über clock)
  clock?, timers?, logger?,
  cronMisfireToleranceMs?, maxRecordedMissedSlots?,
});
await controller.recover();        // vorher!
scheduler.start();                 // erster Planungsschritt sofort, Cron-Timer (inkl. skipped_missed nach Downtime)
await scheduler.stop();            // beim Shutdown vor controller.shutdown(...) bzw. danach – wartet auf laufende Schritte

scheduler.planOnce(): Promise<PlanningStepReport>            // z. B. nach Config-Reload/Override sofort planen
scheduler.startManual(id, { itemRef?, parameters? }): Promise<{ run, done }>
scheduler.dryRun(id): Promise<DryRunResult>                   // inkl. gate (pause/drain/ready)
scheduler.lastDiagnosis(id) / listDiagnoses(): WorkflowPlanningDiagnosis[]   // letzte Planungsdiagnose (GUI/API)
scheduler.lastPlanningStep(): PlanningStepReport | null
scheduler.cronStatus(): CronWorkflowStatus[]                  // nextSlot, lastFiring, lastConditions, enabled
scheduler.whenIdle(): Promise<void>                           // Tests
```

**Fehler → HTTP:** `manual_item_required`, `manual_item_not_supported`, `manual_item_invalid_ref`,
`invalid_parameters` (Details `errors: [{parameter, message}]`) → 400; `manual_item_not_found` → 404;
`config_unknown_workflow` → 404; `lock_conflict` → 409 (`holderRunId`); `source_unavailable` → 502;
`scheduler_not_accepting` → 503.

**Diagnose-Vokabular** (`CandidateDecision`): `started`, `would_start`, `pending_checks` (nur Dry-Run), `filtered`,
`filter_unknown`, `shell_filter_rejected`, `shell_filter_unknown`, `condition_failed`, `condition_unknown`, `locked`,
`blocked`, `workflow_limit`, `global_limit`, `workflow_unavailable`, `gate_closed`, `start_failed`. Jeder Kandidat
trägt Filter-Trace (WI-04), Shell-Filter-/Item-Condition-Diagnosen, Priorität (+ Regelindex), `runId`/`blockId`.
Cron-`decision`-Vokabular: siehe `CronSlotDecision` bzw. `docs/cron-semantics.md`.

## Nebenaufgabe: Flake `shell-executor.test.ts` „controlled cancel → cancelled, even with a result file“
Ursache: SIGTERM geht an die ganze Prozessgruppe. Je nach Scheduling stirbt `sh` selbst am Signal (`signal:
'SIGTERM'`) oder reapt zuerst sein ebenfalls beendetes Vordergrund-Kind (`sleep`) und beendet sich regulär mit
128+15 = **Exit 143**. Der Executor ist korrekt: `cancelled` folgt aus dem Stop-Grund (`stopReason === 'cancel'`),
unabhängig davon, wie der Leader endet, und `classifyOutcome` prüft `cancelled` vor Signal/Exit-Code. Nur der Test
hat das Signal überspezifiziert → Test akzeptiert beide Enden; Klassifikation für Exit 143 / SIGTERM zusätzlich in
`classify.test.ts` festgenagelt. Commit „WI-09: Harden flaky WI-05 cancel test against exit 143“; 6× parallel grün.

## Bewusste Entscheidungen
- **Kapazität vor teuren Prüfungen** im echten Schritt (Ergebnis identisch zu §7-Reihenfolge, spart API-Aufrufe und
  Shell-Checks bei vollen Limits); final wird sie synchron unmittelbar vor `reserve` erneut geprüft.
- **Reihenfolge in Schritt 5:** Workflow-Conditions (einmal pro Schritt) → teurer Filter → Shell-Filter →
  Item-Conditions.
- **Manueller Start ignoriert `enabled`** (Spec §7 listet nur, was er umgeht; `enabled` steuert automatische Starts) –
  erlaubt das Testen deaktivierter Workflows. Bei Bedarf in WI-10 per API-Option verschärfen.
- **Deaktivierte Schedule-Workflows** werden weiter getaktet und protokollieren `skipped_disabled` (lückenlose
  Historie, korrekte Downtime-Erkennung).
- **Prioritätsregeln mit teuren Feldern** lösen diese für alle günstig passenden Kandidaten auf (für die Sortierung nötig).
- Workflow-Conditions eines Workflows ohne Kandidaten werden nicht ausgeführt (lazy) und erscheinen als `not_evaluated`.
- Diagnosen werden pro Workflow auf 500 Kandidaten begrenzt (`omittedCandidates`).
- Kein sofortiges Neuplanen bei Run-Ende; neue Starts nach dem nächsten Poll (Spec: Polling).
