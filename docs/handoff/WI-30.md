## Bewusste Entscheidungen / Abweichungen

- **Lifecycle-Run-Statusfolge:** `reserved → starting → running` (Kette läuft in `running`) → `finalizing` → `completed`.
  So bleibt der bestehende Zustandsautomat unverändert, und `{run.started_at}` ist in `on_retry_unblock` gesetzt
  (Start der Kette). Unterbrochen (erzwungener Stopp) bleibt der Run `running`; die Recovery setzt fort.
- **Platzhalter-Scope `on_retry_unblock`** (WI ließ es offen, konsistent mit §5.2/`on_start`): `result.*` =
  Konfigurationsfehler; `workspace.path` und `parameters.*` erlaubt, aber leer. `{block.cleared_*}` in
  `on_retry_block` = **Konfigurationsfehler** (statt immer leer), weil sie dort nie einen Wert haben können.
- **`{block.cleared_by}`:** der gespeicherte `clearedBy` (mit Anmeldung der Benutzer, sonst der Client-Name – UI `ui`,
  Default `api`; ein CLI-Befehl zum Aufheben existiert nicht); `anonymous`, wenn keiner gespeichert ist.
- **Lifecycle-Runs zählen nicht zu `max_concurrent`** (`countActive`) und nicht als `run.last_*` in Views
  (`lastRunsForItems`) – sonst würde ein `completed`/`success` des Lifecycle-Runs Views/Filter verfälschen. Im
  Controller-Status (`activeRuns`) zählen sie (Drain wartet auf sie).
- **Workflow-Scope (Cron):** Lock-Key `unblock:<runId>`; automatische Starts verhindert `reserve(failIfBlocked)`
  (→ `skipped_blocked`), solange der Lifecycle-Run aktiv ist. Bei Item-Scope hält er das Item-Lock.
- **409 nur mit nicht leerem Hook**, wie im WI; ohne Hook bleibt das Aufheben auch bei laufendem Run erlaubt.
  Während Recovery/Drain wird ein Aufheben mit Hook mit 503 abgelehnt (es könnte kein Run starten).
- **`clearBlock` liefert weiter `BlockRecord`** (rückwärtskompatibel); die Run-ID steht in `block.clearedRunId`.
- **Kennzeichen** `runs.retry_block_hook` wird nur gesetzt, wenn der Block in diesem Übergang entsteht **und**
  `on_retry_block` Actions hat; die Block-Zuordnung läuft über `blocks.run_id` (erzeugend) bzw. `blocks.cleared_run_id`.
- **Fehlschlag des Lifecycle-Runs:** `completed` + `failure` mit Grund `on_retry_unblock action '<id>' failed`. Ein
  späterer manueller Retry/Skip setzt die Kette fort, ändert aber den Endstatus des Runs nicht mehr (wie bei allen
  Hooks beendeter Runs).
