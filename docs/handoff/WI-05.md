### Klassifikation (§8.2, verbindlich)
Reihenfolge: Spawnfehler → `start_error`; Cancel → `cancelled`; Timeout → `timed_out`; Signal → `crashed`;
Exit ≠ 0 → `crashed` (Ergebnisdatei wird ignoriert); Exit 0 + gültig → `completed` + `success|failure`;
Exit 0 ohne Datei → `completed`/`success`; Exit 0 + ungültig/unlesbar/kein reguläres File → `crashed`
(`protocol error: …`). `businessResult`/`result` nur bei `completed` gesetzt. `reason` ist ein kurzer Text
(z. B. `exit code 1`, `idle timeout exceeded`).

### Ablauf `start(spec)`
1. Pfade müssen absolut sein; optional `workspaceBaseDir` (= `workspace.base_dir`): `resolveWithin` vorab und
   `assertRealPathWithin` nach dem Anlegen (Symlink-Ausbruch → `start_error`).
2. Workspace anlegen (`createDirectory`) bzw. Existenz prüfen; `runs/<id>/` anlegen; **veraltete `result.json`
   löschen**; `context.json` atomar (tmp + rename, Mode 0600) schreiben, zusätzlich durch den Secret-Redactor.
3. Logdateien `logs/<id>/{stdout,stderr}.log` (Mode 0600) öffnen – Fehler hier sind **kein** Startfehler,
   sondern `log_write_error`-Diagnose (§12).
4. `spawn(command, args, {cwd, env, detached: true, stdio: ['ignore','pipe','pipe']})` → eigene Session/
   Prozessgruppe, `pgid = pid`. Env = Minimal-Env (`PATH, HOME, LANG, TZ, USER, LOGNAME, TMPDIR`, Fallback-PATH)
   < `spec.env` < `spec.secrets` < `ORCH_*` (Protokollvariablen nicht überschreibbar). Keine Controller-Env.
5. Startidentität erfassen (`startIdentity`; `undefined`, wenn der Prozess schon weg ist).
6. Jede Vorbereitungs-/Spawn-Störung → `wait()` liefert `spawnError` (→ `start_error`); `start()` wirft nicht.

### Logs, Events, Listener
- Logs byte-genau unverändert (bis auf Redaction), stdout/stderr getrennt.
- `maxLogBytes` gilt **pro Stream** (so im Core-Vertrag `ExecutionSpec.maxLogBytes` dokumentiert). Bei Erreichen:
  Datei endet exakt am Limit, genau ein `log_truncated` (mit `stream`, `details.limitBytes`), danach kein
  Schreiben mehr. Live-Output und Event-Parsing laufen weiter.
- Schreibfehler → ein `log_write_error`; `outcome.logs.truncated = true` (Log gilt als unvollständig).
- `outcome.logs.{stdoutBytes,stderrBytes}` = tatsächlich geschriebene Bytes.
- Backpressure nur durch die Logdatei (Pause/Resume der Pipe); Listener (`onOutput/onEvent/onDiagnostic`) werden
  asynchron per `setImmediate` in Emit-Reihenfolge aufgerufen; werfende Listener werden geloggt, stören nichts.
- Zustellung startet erst, nachdem `start()` zurückgekehrt ist → Listener, die direkt nach `await start()`
  registriert werden, verpassen nichts. `wait()` resolved erst, nachdem alle vorherigen Benachrichtigungen
  zugestellt wurden.
- Events: Zeilen mit `@@ORCH_EVENT ` (stdout und stderr), JSON-Objekt mit `type`, Payload ≤ `MAX_EVENT_LINE_BYTES`.
  Ungültig → `event_parse_warning` (mit `details.line`, max. 200 Zeichen). Rohzeile bleibt im Log. CRLF erlaubt.
  Letzte Zeile ohne Newline wird am Stream-Ende ausgewertet.

### Secret-Redaction (best-effort, §20.4/§24.8)
- Exakte Vorkommen bekannter Secret-Werte (≥ 4 Zeichen, plus `\n`-escapte Form mehrzeiliger Werte) werden in
  Logdateien, Live-Output, Events, Diagnosen, Spawn-Fehlertexten, `context.json` und im geparsten Ergebnis
  (`redactValue`, d. h. zusätzlich secret-artige Keys) durch `[REDACTED]` ersetzt.
- Über Chunk-Grenzen sicher: Nur ein Ende, das Anfang eines Secrets sein könnte, wird bis zum nächsten Chunk
  zurückgehalten (normaler Output wird nicht verzögert).
- **Grenzen:** transformierte Secrets (base64, URL-encoded, zeichenweise mit Fremdbytes dazwischen, Teilstücke)
  werden nicht erkannt. Ein Worker kann ihm übergebene Secrets immer leaken – Worker sind vertrauenswürdig.

### Timeouts, Cancel, Supervision (§8.3, §13)
- `maxDurationMs` ab Spawn; `idleTimeoutMs` wird durch **jeden** empfangenen stdout/stderr-Chunk (damit auch
  Events) zurückgesetzt. Auslösung → SIGTERM an die Gruppe, nach `cancelGraceMs` SIGKILL.
- `cancel(graceMs?)`: SIGTERM → Grace → SIGKILL → **Ende bestätigen** (Leader beendet und keine lebenden
  Gruppenmitglieder mehr) → resolved erst, wenn auch das Outcome vorliegt. Gelingt das nicht innerhalb
  `killConfirmMs` (Default 5 s): Diagnose `kill_failed`, `cancel()` rejected mit `OrchestratorError('kill_failed')`,
  `wait()` bleibt offen, bis die Gruppe tatsächlich weg ist (wird dann mit `cancelled` geliefert). Ein erneuter
  `cancel()` versucht es nochmals.
- Erster Stopp-Grund gewinnt (Timeout vs. Cancel). Cancel nach Prozessende ist No-op (kein `cancelled`).
- **Bewusste Entscheidung:** Hinterlässt ein Worker nach normalem Exit noch Prozesse in seiner Gruppe
  (z. B. `cmd &` ohne `wait`), werden diese mit TERM→KILL beendet; das Outcome folgt dem Exit des Leaders.
  Prozesse außerhalb der Gruppe (eigene Session, Container) erfasst das nicht; hält so ein Prozess stdout/stderr
  offen, werden die Pipes nach `stdioDrainMs` (Default 2 s) geschlossen.
- Signale an die **eigene** laufende Gruppe gehen ohne `ps`-Identitätsprüfung: Solange der Leader nicht
  reaped ist, kann seine PID nicht wiederverwendet werden; solange Gruppenmitglieder existieren, kann die PGID
  nicht neu vergeben werden. Nach Leader-Ende wird nur signalisiert, wenn die Gruppe noch existiert.
- Linux: Zombies zählen beim „Gruppe weg?“-Check nicht (Scan von `/proc/*/stat`), damit ein nicht reapender
  PID 1 im Container kein falsches `kill_failed` erzeugt. Trotzdem empfohlen: Container mit Init (`--init`/tini).

### Startidentität (§13) – für WI-08 Recovery
- Token: Linux `linux:<boot-id>:<starttime>` (Feld 22 von `/proc/<pid>/stat`, `comm` mit Klammern/Spaces robust
  geparst); macOS `darwin:<lstart>` via `/bin/ps -o pgid=,lstart= -p <pid>` mit `LC_ALL=C`, `TZ=UTC`
  (Sekundenauflösung). Andere Plattformen: keine Identität → nie signalisieren.
- `checkProcessIdentity(identity) → 'same' | 'different' | 'gone' | 'unknown'` (`unknown` bei Fehlern oder wenn
  derselbe Prozess die Gruppe gewechselt hat).
- `killProcessGroupIfSame(pgid, identity, signal) → {signalled:true} | {signalled:false, reason}` signalisiert nur
  bei `same` und `pgid === identity.pgid`; PIDs ≤ 1 werden nie signalisiert.
- Hinweis Recovery: Ist der Leader weg, aber die Gruppe hat noch Mitglieder, liefert die Prüfung `gone`, es wird
  nicht signalisiert. WI-08 sollte dann `processGroupAlive(pgid)` prüfen und den Run als `recovery_pending`
  (sichtbarer Recovery-Fehler) statt `crashed` behandeln.

## Offene Punkte
- **Linux nicht lokal ausgeführt** (Docker-Daemon nicht verfügbar). Linux-Pfade sind per simuliertem procfs
  getestet; die Prozess-Tests verwenden nur POSIX-`sh`-Features (dash-kompatibel) und laufen dort ohne Änderung.
  Vor Merge/Release einmal `npm run check` auf Linux laufen lassen.
- Prozess-Supervisor-Spike Linux (systemd-Scopes/cgroups, §24.3) bleibt außerhalb des Umfangs.
- macOS-`lstart` hat Sekundenauflösung: PID-Wiederverwendung in derselben Sekunde würde nicht erkannt
  (praktisch ausgeschlossen, dokumentiert).
