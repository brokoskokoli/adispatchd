### Evaluator
- Kleene-Logik: `all` false bei einem false, sonst unknown bei einem unknown; `any` dual; `not unknown = unknown`;
  `all: []` = true, `any: []` = false, fehlender Filter = true.
- `known: false` → Prädikat `unknown` (mit `reason`), nie 0/leer. Resolver-Exceptions, malformed Nodes → `unknown`, wirft nie.
- **Lazy:** In `all`/`any` werden Kinder ohne teure Felder (`FieldSource.isExpensive`) zuerst ausgewertet (sonst
  Originalreihenfolge), Kurzschluss sobald das Ergebnis feststeht; übersprungene Kinder erscheinen im Trace als
  `not_evaluated`. Jedes Feld wird pro Auswertung höchstens einmal aufgelöst.
- **Trace** spiegelt den AST (Kinder in Originalreihenfolge) mit `path` (`$`, `$.all[1].not`, …), `value`
  (`true|false|unknown|not_evaluated`), bei Prädikaten `field/operator/expected/actual?/reason?`.

### Operator-Semantik (bewusste Festlegungen)
- `null` ist ein **bekannt leerer** Wert: `equals null` true nur für null; `contains`/`in` auf null → false;
  `greater_than/less_than` mit null → unknown.
- `equals`/`not_equals`: gleicher JS-Typ nötig, sonst unknown; Arrays vs. Arrays als Mengenvergleich; Array vs. Skalar → unknown.
- `contains`: Array enthält Skalar bzw. String enthält Teilstring; Array-Operand oder unpassende Typen → unknown.
- `in`: Operand muss Array sein; Skalarfeld ∈ Liste; **Array-Feld: true bei nicht-leerer Schnittmenge**; keine
  typgleichen Listenelemente → unknown.
- `greater_than`/`less_than`: Zahl/Zahl, String/String (Code-Unit-Reihenfolge), Felder vom Typ `date` als
  Zeitpunkte (unparsebar → unknown); alles andere (boolean, Arrays, Mischtypen) → unknown.
- Datumsfelder werden bei `equals` ebenfalls als Zeitpunkt verglichen (Typ aus `FieldDefinition` über `FieldSource.fieldType`).

### `createItemFieldSource` (Batch-Vertrag)
- Günstige Felder aus `item.fields`; deklariert aber nicht geliefert → unknown („not provided“), unbekanntes Feld → unknown.
- Beim ersten benötigten teuren Feld **ein** `resolveFields`-Aufruf mit allen teuren Feldern aus `wantedFields`
  (Aufrufer übergibt z. B. `collectFields(filter)` + Felder der Prioritätsregeln); Ergebnis memoisiert für die
  Lebensdauer der FieldSource (= ein Planungsschritt/View-Request), nichts wird in `item.fields` geschrieben.
  Fehlender Eintrag/Exception/kein Resolver → `known:false`.
- `extraFields` für nicht vom Adapter stammende Werte (Views: `run.last_workflow`, `run.last_result.message`, …), Wert oder `FieldResolution`.

### Pushdown
Konservativ: nur Prädikate einer Top-Level-Konjunktion (verschachtelte `all` werden geflacht), Feld deklariert,
nicht `expensive`, Operator in `pushdown` **und** `operators`. `any`/`not` bleiben lokal. `pushdown ∧ local ≡ filter`;
da Adapter gepushte Teile ignorieren dürfen, sollte der Aufrufer trotzdem den vollen Filter lokal auswerten.

### Priorität und Sortierung
- `resolveItemPriority`: erste Regel mit `true` gewinnt, `false`/`unknown` matchen nicht, sonst `default`
  (ohne Config 0); Traces pro Regel, Regeln nach dem Treffer `not_evaluated`.
- `compareCandidates`: Workflow-Priorität desc → Item-Priorität desc → `createdAt` asc (fehlend zuletzt) →
  `itemKey` asc (natürlich: `x:9` < `x:10`, locale-unabhängig) → `workflowId` asc. Totale Ordnung, unabhängig von der Eingabereihenfolge.

### Shell-Check-Runner
- `spawn` mit Argumentliste (äquivalent zu `execFile`, aber mit eigener Prozessgruppe und Ausgabelimit),
  `shell: true` nur explizit (`/bin/sh -c <command> sh <args…>`). stdin = ignore, cwd = Temp-Verzeichnis des Checks (oder `spec.cwd`).
- Env: nur `PATH, HOME, LANG, TZ, USER, LOGNAME, TMPDIR` (aus injizierbarem `hostEnv`) + `spec.env` +
  `ORCH_CHECK_CONTEXT_FILE` (JSON-Datei, Modus 0600, in eigenem `mkdtemp`-Verzeichnis, danach gelöscht).
- Exit 0 → true, 1 → false; ≥2, Signal, Timeout, Spawnfehler (z. B. ENOENT), Abort → `unknown` mit `error`.
  Timeout/Abort: SIGTERM an die Prozessgruppe, nach `killGraceMs` (Default 2 s) SIGKILL. Nach Ende wird die Gruppe
  zusätzlich per SIGKILL abgeräumt; Hintergrundkinder, die die Pipes offen halten, blockieren nicht (max. `killGraceMs`).
- Ausgabe: stdout/stderr je bis `maxOutputBytes` (Default 16 KiB), Rest verworfen, `outputTruncated`.
- Cache: `runCached(key, ttlMs, spec, ctx)` – Clock-basiert, Ablauf bei `now - storedAt >= ttl`, **nur true/false
  werden gecacht** (Prüffehler werden beim nächsten Planungsschritt erneut versucht), parallele Aufrufe mit gleichem
  Key teilen eine Ausführung, `ttlMs <= 0` = kein Cache, `invalidate(key?)` (z. B. nach Config-Reload).
  Item-Conditions/Shell-Filter: einfach `run()` verwenden (kein Cache).
- `buildCheckContext(kind, workflowId, item?, sourceType?)` → `{schema_version:1, kind, workflow:{id}, source?:{id,type,item_id,item_key,url,item_type,created_at?,attributes}}`.

## Hinweise für Konsumenten
- **WI-09 (Scheduler/Dry-Run):** pro Kandidat eine `createItemFieldSource(item, {definitions: adapter.fieldDefinitions(),
  resolveFields: (i, f) => adapter.resolveFields(i, f), wantedFields: [...collectFields(filter), ...Prioritätsfelder]})`,
  dieselbe FieldSource für Filter und `resolveItemPriority` verwenden. Sortieren mit `sortCandidates`.
  Shell-Filter/Conditions im Dry-Run nicht ausführen – als `not_evaluated` darstellen (für Shell-Checks gibt es
  keinen AST-Trace; WI-09 baut dafür eigene Diagnose-Einträge aus `ShellCheckResult` bzw. `not_evaluated`).
  Cache-Key-Vorschlag für Workflow-Conditions: `<workflowId>:condition:<index>`.
  Teure Felder im Dry-Run werden normal (deklarativ) ausgewertet.
- **WI-10 (Views):** `evaluateFilter` mit `createItemFieldSource(..., {extraFields: run.last_*})`; keine Shell.
- `ShellCheckSpec.timeoutMs` erwartet ms (WI-02 liefert normalisierte Durations); `args`/`shell` sind optional.
  WI-02 sieht laut Work-Item für `shell_filter` nur `command`/`timeout` vor – `shell: true` ist im Runner
  vorhanden, aber nur nutzbar, wenn die Config es anbietet.

## Offene Punkte / Abweichungen
- `spawn` statt `execFile` (gleiche Sicherheitseigenschaft – keine Shell –, aber nötig für Prozessgruppen-Kill und Ausgabelimit).
- Sicherheitsnetz Prozessgruppe nur POSIX (`process.kill(-pid)`), Windows nicht unterstützt (Zielplattform Linux).
- Secrets für Shell-Checks sind nicht vorgesehen (Spec nennt keine); bei Bedarf über `spec.env` vom Aufrufer.
- Die Semantik von `in` mit Array-Feldern (Schnittmenge) und `contains` auf Strings ist eine eigene Festlegung (Spec schweigt).
