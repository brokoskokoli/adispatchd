### Ablauf `runHook(run, hook, snapshot?, context?)`
1. Busy-Guard pro Run (zwei Ketten desselben Runs nie parallel → `LifecycleBusyError`).
2. Journal via `actions.createJournal(run, hook, …)` aus `snapshot.workflow.hooks[hook]`: Ordinal = Position,
   `action_name` = Config-ID (`on_success.1` bzw. explizite `id`), `action_config_json` = normalisierte Action-Config
   (inkl. aufgelöster `retry`-Policy und `continueOnError`). Existiert das Journal schon, wird es unverändert genutzt
   (→ `runHook` ist idempotent/fortsetzbar; ein abgeschlossener Hook führt nichts erneut aus).
3. Sequenziell: `succeeded`/`skipped` überspringen; `failed` ohne `continue_on_error` → Kette steht (`status: failed`);
   `pending` → ausführen. Jede Statusänderung wird vor dem Weiterarbeiten persistiert.
4. Pro Action: `startAttempt` → Versuch → `finishAttempt` (+ `external_key`, `error_json`) → bei Erfolg `succeeded`;
   bei Fehler: weiterer Versuch nach Delay (Action bleibt währenddessen `running`) oder `failed`.
5. `runs.lifecycle_status`: während der Kette `running`, danach aggregiert über **alle** Hook-Ketten des Runs:
   `running` > `failed` (irgendeine Kette steht an einer `failed`-Action ohne `continue_on_error`) > `pending` > `succeeded`.
   Ein gescheitertes `on_start` bleibt also als `failed` sichtbar, auch wenn danach `on_start_error` erfolgreich lief –
   bis es per Retry/Skip erledigt ist (deckt sich mit der Retention-Schutzregel aus WI-03).

### Retry
- Policy aus dem Journal (`config.retry`, von WI-02 bereits aus Action-Override über `lifecycle.action_retry` gemergt);
  Fallback 3 × 30 s. Delay über `Timers` (`sleep(timers, …)`), mit `FakeClock` ohne echtes Warten testbar.
- Delay = `max(policy.delayMs, error.retryAfterMs)` (Rate-Limit `Retry-After` wird respektiert).
- **Nicht wiederholbare Fehler** (`SourceError.retryable === false`: `auth`, `forbidden`, `not_found`, `invalid`;
  Template-Fehler; fehlende Source/Item/Identity) beenden die Versuche sofort → `failed`. Bewusste Abweichung vom
  wörtlichen „3-mal versuchen“: Wiederholen kann hier nicht helfen; manueller Retry bleibt möglich.
- Unerwartete Exceptions gelten als wiederholbar. Alle Shell-Fehler (Exit ≠ 0, Signal, Timeout, Startfehler) sind wiederholbar.
- `ActionErrorInfo` (= `error_json`/`last_error_json`): `{code, message, retryable, outcomeUnknown?, kind?, status?,
  retryAfterMs?, details?}`; Texte optional über `redact` (z. B. `SecretRedactor.asRedactor`) und `redactValue`.

### Idempotenz `source.comment`
- Marker `commentMarker(runId, actionId)` (Journal-ID) → Adapter hängt `<!-- orch:… -->` an.
- Template wird **vor** jedem API-Aufruf gerendert (Template-Fehler posten nie etwas).
- Hatte die Action schon einen Versuch (egal ob Fehler mit bekanntem oder unklarem Ausgang, manueller Retry,
  Recovery), wird vor dem Posten `findCommentByMarker` aufgerufen; gefunden → `succeeded` mit `external_key`
  (Event-Detail `reconciled: true`). Scheitert die Suche selbst, scheitert der Versuch – es wird nie ohne
  erfolgreiche Suche erneut gepostet.
- `source.update`: `applyUpdate` liest das Item neu und ändert nur Abweichungen → einfaches Wiederholen ist sicher.

### Identitäten
`source.comment`: Action-`identity` → Workflow-`identity` → Source-`identity`; `source.update`: Workflow → Source
(`resolveActionIdentity`). Lesen (`getItem`) macht der Adapter mit der Source-Identity.

### Platzhalter (Scopes exakt wie WI-02-Tabelle)
Modus `text`, Scope `{run, workspace, source: trigger.type === 'source', result: hook !== 'on_start',
parameters: deklarierte Namen}`; gerendert mit `renderTemplate` → unbekannte/nicht verfügbare Platzhalter werfen
`TemplateError` (nicht wiederholbar), auch wenn die Config-Validierung umgangen wurde. Werte:
`run.*` aus dem Run, `workspace.base_dir` aus dem Snapshot, `workspace.path` = `runs.workspace_path`,
`source.*` aus Snapshot (`repository` vom Adapter), `item.*` aus dem Item (`number` = numerische `itemId`,
`title` aus `fields.title`), `result.status|result` = `runs.final_status|business_result`,
`result.message` = `runs.result_json.message`, `parameters.*` = `runs.parameters_json`.

### Shell-Actions
- Über `Executor` (Default: `new ShellExecutor({clock, logger})`) → Minimal-Env (`PATH, HOME, LANG, TZ, USER, LOGNAME,
  TMPDIR`) + gerenderte `env` + `ORCH_*`; **keine Controller-Env, keine Secrets**.
- Kontext-JSON (`ORCH_CONTEXT_FILE`, Typ `ShellActionContext`): `schema_version, kind: 'lifecycle_action', run{id,
  trigger, status, started_at, finished_at}, workflow, hook, action{id, name, ordinal, type, attempt}, source{… wie
  WorkerContext.source} (→ ORCH_SOURCE_*), parameters, workspace{path, base_dir}, result{status, result, reason,
  message, details, artifacts} | null (on_start)`.
- Dateien pro Versuch: `data/runs/<run>/actions/<actionId>/attempt-<n>/{context.json,result.json}`,
  Logs `data/logs/<run>/actions/<actionId>/attempt-<n>/{stdout,stderr}.log` (Pfade stehen im Fehler-`details.logs`).
- cwd: Run-Workspace, falls vorhanden; sonst `…/attempt-<n>/cwd` (z. B. `on_start` vor Workspace-Anlage oder nach Cleanup).
- Timeout = Action-`timeout` (`maxDurationMs`), Grace `shellCancelGraceMs` (Default 5 s), Log-Limit `maxShellLogBytes`
  (Default 10 MiB). Erfolg = Exit 0; Ergebnisdatei wird ignoriert.

### Persistierte Events (`run_events`, origin `orchestrator`)
- `lifecycle.action` `{actionId, hook, ordinal, type, name, status, externalKey?, attempt?, error?, retryInMs?, details?,
  manual?, recovery?, abandoned?, interrupted?}` – in derselben Transaktion wie die Statusänderung.
- `lifecycle.chain` `{hook, status: running|succeeded|failed|interrupted, failedActionId?}`.

### Notification
`lifecycle_action_failed` über `Notifier.notify` (Core-Interface) **nur via `afterCommit`**, genau einmal, wenn eine
Action ohne `continue_on_error` endgültig scheitert (bzw. eine unterbrochene Shell-Action in Recovery auf `failed`
gesetzt wird). Payload `LifecycleActionFailedPayload`: `runId, workflowId, hook, actionId, actionName, actionType,
ordinal, attempts, error (ActionErrorInfo), sourceItemKey, sourceUrl`. Mit `continue_on_error` gescheiterte Actions
melden **nicht** (Kette läuft weiter; sichtbar über `listFailed`). Werfende Notifier werden geloggt, nie propagiert.

## API für WI-08

```ts
const lifecycle = new LifecycleEngine({
  repositories: persistence,            // runs, actions, events, transaction, afterCommit
  sources: (sourceId) => adapters.get(sourceId),
  dataDir,
  notifier,                             // WI-10: persistiert + stellt zu; hier nur Callback
  onActionChange: (action) => bus.publish(...),   // optional, nach Commit
  executor?, clock?, timers?, logger?, redact?, shellCancelGraceMs?, maxShellLogBytes?,
});

runHook(run: RunRecord | string, hook: HookName, snapshot?: WorkflowSnapshot, ctx?: { item?, signal? }): Promise<HookResult>
retryAction(actionId: number, ctx?): Promise<HookResult>   // nur 'failed'; frische Versuchsrunde, dann Kette fortsetzen
skipAction(actionId: number, ctx?): Promise<HookResult>    // 'failed'|'pending' → 'skipped', dann Kette fortsetzen
resumeIncomplete(run, { hooks?, item?, signal? }): Promise<HookResult[]>   // Recovery nach Neustart
abandonHook(run, hook, { item? }): Promise<HookResult>      // Rest einer Kette verwerfen (pending → skipped)
isBusy(runId): boolean

interface HookResult {
  runId; hook;
  status: 'succeeded' | 'failed' | 'interrupted';
  actions: RunActionRecord[];          // Endstand des Hook-Journals
  failedAction: RunActionRecord | null // Action, an der die Kette steht
}
```

Hinweise/Verträge:
- **Vor `runHook` persistieren**: Snapshot (`runs.config_snapshot`), bei Abschluss-Hooks `beginFinalization(target)`
  und `update({result})` – die Engine liest Run/Result immer frisch aus der DB (identisch für Erstlauf, Retry, Recovery).
  `snapshot`-Parameter ist optional (Default `run.configSnapshot`) und muss der Run-Snapshot sein.
- `ctx.item`: frisch gelesenes Item (spart einen API-Call, liefert `{item.title}`); ohne Item liest die Engine es selbst.
- **`on_start`**: `status === 'failed'` → Worker nicht starten (WI-08 entscheidet `start_error`). `interrupted` nur bei Abort.
- **Recovery**: `actions.runIdsWithIncompleteActions()` → je Run zuerst entscheiden, welche Ketten noch sinnvoll sind.
  Beispiel: Run stand in `starting` während `on_start` → wird `crashed`: `abandonHook(run, 'on_start')`, dann
  `runHook(run, 'on_crash')`; andernfalls `resumeIncomplete(run)` (optional `{hooks: [...]}`).
  `resumeIncomplete` macht zuerst alle `running`-Actions sicher: Comment → Marker-Abgleich (gefunden → `succeeded`,
  sonst `pending`); Update → `pending` (idempotent erneut); **Shell mit offenem Versuch → `failed`** (Ausgang unklar,
  alter Prozess könnte noch laufen; kein automatisches Wiederholen, Notification) – bewusste Entscheidung, Spec nennt
  für Shell kein Verfahren. Danach werden nur Ketten fortgesetzt, die nicht an einer `failed`-Action stehen.
- **Shutdown**: `ctx.signal` bricht Retry-Delays ab (Action → `pending`, `status: 'interrupted'`) und cancelt laufende
  Shell-Actions; laufende GitHub-Aufrufe werden zu Ende geführt. Danach `resumeIncomplete` beim nächsten Start.
- `retryAction`/`skipAction` auf einen beendeten Run ändern nur Journal und `lifecycle_status`, nie den Run-Status;
  der Haupt-Worker wird nie neu gestartet. Die API (WI-10) kann die Promise fire-and-forget starten
  (Retry-Delays können dauern) und `LifecycleBusyError` (`lifecycle_busy`) als 409 melden;
  `lifecycle_not_retryable` / `lifecycle_not_skippable` → 409/400.

## Offene Punkte
- Ein manueller Retry eines `on_start`-Fehlers nach bereits erfolgtem `on_start_error` würde `on_start` nachholen
  (Labels!). Die Engine verhindert das nicht; WI-08/WI-10 sollten Retry nur für sinnvolle Hooks anbieten bzw.
  `abandonHook` nutzen.
- Ein Hook wird pro Run nur einmal journalisiert (WI-03-Design); ein zweiter Durchlauf desselben Hooks ist nicht vorgesehen.
- Shell-Action-Logs/-Kontexte liegen unter dem Run-Verzeichnis; Retention (WI-10) muss `runs/<id>` und `logs/<id>`
  komplett löschen.
