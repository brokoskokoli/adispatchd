# Handoff WI-11 – Weboberfläche

Branch `wi-11-web-ui` (Basis: `main` mit „Merge WI-10“). Gate `npm run check` grün (70 Testdateien, 655 Tests, inkl.
Typecheck der Browser-Quellen). `npm run build` erzeugt `dist/` inkl. `dist/ui/public`. Keine neuen Dependencies.

## Entscheidung: Vanilla TypeScript, nur `tsc`
- Browser-Code in TypeScript ohne Framework und ohne Bundler; `tsc -p tsconfig.ui.json` erzeugt ES-Module
  (`dist/ui/public/js/**`), die der Browser direkt per `<script type="module">` lädt. Gründe: keine neue Dependency,
  gleiche Toolchain wie der Rest (Typecheck im Gate), die UI ist klein genug für direkte DOM-Erzeugung; Preact o. ä. hätte
  ohne Bundler nur Vendoring einer Fremddatei bedeutet.
- Aufteilung: `src/ui/shared/` = DOM-freie, reine Logik (im Haupt-`tsconfig` enthalten → läuft unter Node/vitest, DOM-Freiheit
  wird vom Compiler erzwungen); `src/ui/client/` = DOM-Code (nur in `tsconfig.ui.json`, im Haupt-`tsconfig` ausgeschlossen).
- Hash-Routing (`#/runs/<id>?tab=logs`) → kein Server-Fallback nötig, `@fastify/static` liefert nur Dateien.

Live-Updates: SSE-Nachrichten lösen pro Seite gedrosselte REST-Reloads aus (max. 1×/s, nie parallel); Events werden im
Events-Tab direkt angehängt; Logs werden bei `run.output` per REST ab `end` nachgeladen (exakte Bytes, keine Duplikate/Lücken,
Polling alle 5 s als Fallback). Nach Reconnect/`stream.reset` lädt die aktuelle Seite per REST neu. Formulare werden während
der Eingabe nicht überschrieben; geöffnete `<details>` bleiben bei Re-Render offen.

## Bewusste Entscheidungen / Hinweise
- `MessageEvent.lastEventId` wird **nicht** zur Erkennung persistenter Events benutzt (der Browser überträgt die letzte ID auf
  nachfolgende nicht-persistente Nachrichten → sie wären als Duplikat verworfen worden; Regressionstest vorhanden). Maßgeblich
  ist `id` im JSON-Payload.
- CSP als `<meta>` (kein Eingriff in `src/api/`); `frame-ancestors` ist per Meta nicht möglich, `X-Frame-Options: DENY` kommt
  aus WI-10. Optional später als HTTP-Header für die UI-Antworten.
- Views laden nur beim Öffnen/„Refresh“ (Source-API-Kosten), kein Live-Auto-Refresh.
- Runtime-Override-Formular sendet alle drei Felder; leer = `null` = YAML-Wert.
- Externe Links nur `http(s)` mit `rel="noopener noreferrer"`, sonst Text.
- Entwicklung aus `src/` (`npm run dev -- start …`) nutzt `dist/ui/public` → vorher `npm run build:ui`.

## Review-Runde 1 (Address review findings)
1. **major – Events-Lücke/unbegrenztes Wachstum:** neue `shared/events.ts` (`EventList`, Unit-Tests `events.test.ts`): Cursor =
   höchste zusammenhängend geladene Sequenz; solange `eventsTruncated`/`hasMore` oder nach einer Lücke werden Live-Events nicht
   angehängt, stattdessen Hinweis + „Load newer events“ ab Cursor; Live-Events während eines laufenden Requests halten `pending`;
   veraltete Antworten (anderer Cursor) werden verworfen; nach SSE-Reconnect wird ab Cursor nachgeladen; DOM auf 5000 Zeilen begrenzt.
2. **minor – Stream-Wechsel während Follow:** Generationszähler in `pages/run.ts` (`logGen`): `tail`/`start`/Stream-Wechsel starten
   eine neue Generation, Antworten älterer Generationen werden verworfen (Reset erzwungen). Im Browser geprüft: 8 schnelle
   stdout/stderr-Wechsel während Follow, keine vermischten Zeilen.
3. **minor – `aria-sort`:** `table()` (`client/ui.ts`) akzeptiert Header-Zellen mit Attributen (`HeaderCell`); Views setzen
   `aria-sort` (ascending/descending/none) auf das `<th>`.
4. **nit:** Lifecycle-Badge im Run-Overview bei `lifecycleFailed` immer Ton `error`.
