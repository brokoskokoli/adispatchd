# Handoff WI-41 – Drain über API, CLI, UI und Hub ohne Frist

Branch `wi-41-unbounded-api-drain`, Worktree `../orchestrator-wt/wi-41`. Fehlerbehebung auf 0.11.0; Version nicht
geändert, CHANGELOG-Abschnitt „Unreleased“ (Behoben). Kein DB-Schema-Wechsel, keine neuen Formate oder Dependencies.

## Ursache

`createApp` reichte beim API-Drain (`POST /api/v1/shutdown/drain`) `options.drainTimeoutMs` an
`controller.shutdown` weiter, sobald eine Frist konfiguriert war („without a deadline unless one was configured“).
`--drain-timeout` hat in der CLI einen Default (10m), der Hub übergibt ihn jedem Workspace, `service install` schreibt
ihn in jede Unit – unter dem Hub und unter systemd war ein API-Drain also immer begrenzt. Beobachtet am
15. November 2026: `hub.drain-all`, zehn Minuten später „drain timeout exceeded, cancelling remaining runs“, ein
Coder-Run abgebrochen (Exit 143).

## Entscheidungen und Abweichungen

- **Rückfall des Hubs bleibt begrenzt.** Ist die Steuer-API eines Workspaces auch nach den Wiederholungen nicht
  erreichbar (Startphase vor dem Schreiben von `control.token`, hängender Prozess), bleibt nur SIGTERM, und das drainiert
  der Workspace mit seiner `--drain-timeout`. Ein Workspace ohne Steuer-API hat in der Startphase keine aktiven Runs (der
  Token wird beim Listen geschrieben, die Recovery startet danach). Die Wiederholungen laufen im Hintergrund: `drain`
  kehrt nach dem ersten Versuch zurück (`transition: draining`).
- **Cancel-Frist des API-Drains** bleibt `--cancel-timeout` (wie das Signal), damit ein API-Drain während eines
  Signal-Drains nichts verschärft.
- README EN/DE und Website: keine falsche Aussage gefunden (sie nennen `--drain-timeout` nur für SIGTERM), daher
  unverändert. UI-Texte („running runs finish normally“) waren schon richtig.
